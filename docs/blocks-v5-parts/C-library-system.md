# C · 封装与库体系

（积木第 5 版“基础设计”的一部分。作者：C。2026-11-25。只有文档，没有改任何产品代码，没有碰 git，没有安装任何东西。）

## 0. 结论摘要

1. **四层的分法成立，但“通用宿主接口”要拆开**：判定只看一条——**碰不碰外面的世界**。碰（打印、时钟、随机、网络、端口、文件、页面）＝宿主原生接口（L0）；不碰、只是算（JSON、百分号编码、哈希、Base64）＝标准库（L2）。第 4 版把 JSON 和编码算进“通用宿主”，建议改归标准库。判定流程见第 2 节，六个问题走完就知道一个新能力归哪层。
2. **库是一个文件夹**：一份清单 `lib.json` ＋ 若干模块文件 ＋（可选）原生实现、组件、规则、用例、示例、文档、图标。**内置库、用户库、项目自己的积木是同一种格式**；只增字段不改名；每个字段读的时候先判类型，坏的那一截当默认值，坏的条目逐条跳过，整份不崩。完整字段表和一个写全了的示例库见第 3 节。
3. **“一块积木”和“一个定义”分开存**：第 4 版第 2 阶段是“一个函数带一个外观”。库需要“一个定义带几个外观、外观里预先填好几个参数”（同一个“登记路由”函数，做成“当收到 GET …”帽子）。所以模块文件里分 `decls`（定义）和 `blocks`（积木外观，指向某个定义）。旧的写法（函数里直接带 `look`）当成简写，照常能读。
4. **库的标识是两段**：`作者段/库名`，只许小写英文字母、数字、连字符（学 Composer 和 npm 的“作用域”，不学 Maven 的倒写域名——用户没有域名）。显示名另外存，可以是中文。两个库都有“回应”积木不冲突：存盘时积木记的是“库标识＋积木编号”，积木盒里各在各的分类。
5. **版本用三段数字**（语义化版本的主干：大改.加功能.修问题），不用预发布后缀。**一个项目里一个库只留一个版本**；两个库要同一个库的不同大版本＝冲突，拦下来说清楚是谁和谁，不做“两版并存”。大改到不兼容时建议**换标识**（学 Go 的思路）。
6. **可见性三档**：公开 / 库内 / 模块内（默认）。项目“用上”一个库以后，积木盒多一个以库名命名的分类，里面只有公开的积木；公开的类型进类型选择器，公开的组件进控件面板。
7. **校验规则四种声明式**（第 4 版是三种，推演后加一种）：槽约束、位置约束、唯一约束、**槽间约束**（一个槽的可选范围取决于另一个槽）。34 条里只有 S08“被前面的接口挡住”声明不出来，做成应用里**有名字的检查器**，内置库和用户库都按名字引用，用户不能新写检查器。
8. **原生绑定只有一种机制**：一个带签名的声明 ＋ 每种语言一段函数体。生成出来一律是一个包装函数，调用处就是普通调用。“原生片段”不另设机制——它就是“只在本项目里用的原生绑定”。**用户库允许写原生绑定**，但默认关着，要在库的设置里打开“允许手写代码”；带手写代码的积木角上有“手写”标记；导入带手写代码的库要先看代码再点允许；Agent 写手写代码要过确认卡。
9. **最小原生接口**：后端第一批 8 个（打印、读环境变量、现在的时间、睡眠、安全随机字节、发网络请求、开 HTTP 服务、进程级格子的“读”和“原子改”），第二批 5 个文件接口。浏览器建议最小集是**一组通用的“碰 JS 对象”接口（7 个）**＋与后端同名的 5 个通用接口，DOM、定时器、本地存储、地址栏都能在它上面用积木封装；Vue / React 下“改控件”要走语义级接口，这部分由 D 细化。
10. **第 4 版清单里的 `store.get / store.set` 不够**：Go、Java 是多线程处理请求（现有小库里有锁），读出来改完再写回去中间会被别的请求插队。必须换成 `store.read` ＋ `store.update(名字, 函数)`（原子地改）。
11. **库的用例在手机上不装环境也能跑**：把库和用例生成 JavaScript，放进应用自带的网页内核（工程里已有 `webview_flutter`）跑，宿主接口换成“假宿主”（假请求、固定时钟、固定随机）。装了运行环境的，再多一个“在所有语言里跑”，逐字节比对。
12. **迁移**：旧文档一个字不改就能开；旧 op 名由内置库的“旧名对照表”认；“我的积木”＝项目自己的一个隐含库，存盘位置和格式不动。
13. **纸面自查的结论是“只靠函数＋类＋外观＋原生绑定不够”，记了 15 个缺口**（GAP-C-1 … 15，见第 14 节和文末清单；其中 9 个这份文档给了办法，6 个要别的部分接）。第 4 版 7.1 的小路由例子照原样跑不通（14.3）。最要紧的六个：一个定义多个外观（1）、隐含的上下文参数（4）、调用处展开的积木（3）、库的设置项和“最后启动”钩子（6、7）、格子的原子修改（8）、没有“字节串”类型（9）。
14. **没核对 / 没跑的**：五种语言装第三方包的命令、Blockly 插件机制、App Inventor 扩展的官方页面、Snap! 手册的现行版本、浏览器接口的细节（归 D）；示例库没有被任何程序读过或生成过（现在没有读库的代码）；所有返工量都是估计。只跑过三个几行的小实验：示例库的 JSON 和正则读得过；“生成编号”那三行原生代码在本机 Node 24 / Python 3.12 / Java 21 下各跑了一次（第 3.4 节）；Go 里“大写开头才对包外公开”（第 4.3 节）。PHP 一概没跑。

需要霜霜拍板的 3 件：用户库能不能写手写代码（建议：能，默认关）；要不要“从网址导入库”（建议：先不做）；Java 的第三方包这一轮做不做（建议：不做）。

## 1. 现状（读代码看到的）

### 1.1 现在“封装”做到哪了

| 东西 | 在哪 | 现状 |
| --- | --- | --- |
| “我的积木”的外观 | `lib/lang/custom_block.dart`（418 行） | `CustomBlockLook`：名字、形状、文案模板、槽表、颜色键、说明。形状六种里 `cap`（收尾型）`hat`（帽子型）只占位；槽五种里 `inlineMouth` `callbackMouth` 只占位，用了报 B08 |
| 改参数联动 | `lib/lang/custom_block_edit.dart`（217 行） | `remapCallArgs` / `remapLook`：参数增删改名换序后，各处调用和外观跟着变，丢掉的内容列清单 |
| 存盘 | `backend.lc.json` 的 `functions[]` | 每条 `{id: "f1", look, params, body, x, y}`；调用写成 `call:f1`；实参按参数名存 |
| 原生的口子 | `lib/lang/ast.dart` | `LNativeDecl(name, params)`（只有签名）、`LNative(name, args)`（调用）、`LHost(payload)`（宿主自己的语句，语言核心看不懂）。**都还没有“每种语言的实现放哪”的设计** |
| 模块 | `LModule(name, uses, decls, body)` | 节点在，`uses`（用上的模块）标着“第 7 阶段”，没接 |
| 前端自定义组件 | `lib/lowcode/component_model.dart`（89 行） | `LcComponentDef`：编号、名字、属性表（文字 / 数字 / 颜色 / 是否四种）、一棵控件子树；没有插槽、没有事件、没有自己的逻辑 |

**一个定义只能有一个外观**，外观只能绑在“文档里的函数”上（不能绑在方法、构造、别的库的函数上）。这是库体系要补的第一处。

### 1.2 现在后端的“路由、请求、响应、集合”是怎么来的

每种语言手写在运行时小库里，积木只是调它们。按文件里的小节数的行数（粗算，含空行和注释）：

| 语言 | 数据集合 | 读请求 | 写响应 | 路由与启动 | 请求别的网址 | 文件 |
| --- | --- | --- | --- | --- | --- | --- |
| Node | 60 | 60 | 32 | 83 | 39 | `runtime_node.dart` 一个文件 |
| Python | 80 | 78 | 20 | 约 90 | 41 | `runtime_python.dart` 一个文件 |
| Go | 约 129 | ↘ | ↘ | 共 476（`runtime_go_server.dart`） | 133 | 三个文件 |
| Java | 98 | 27 | 15 | 291（`runtime_java_server.dart`） | 77 | 两个文件 |
| PHP | 184（`runtime_php_data.dart`，文件加锁） | ↘ | ↘ | 共约 257（`runtime_php_server.dart` 去掉请求别的网址） | 78 | 两个文件 |

合起来大约 **2200 行手写代码，同一套逻辑写了五遍**。读下来，里面其实混着三种东西：

1. **真的没法用积木搭的**：从网卡读一个请求、把字节写回去、开端口、文件锁。
2. **纯逻辑**：路径按 `/` 切段比对、`:名字` 记进参数表、405 还是 404、网址参数按 `&` `=` 切、状态码不在 200–599 当 200、集合的增删改查、自动编号。这些就是第 4 版说的“该用积木写一份”的部分。
3. **藏在小库里的规矩**（迁移时最容易漏）：
   - 请求内容超过 1MB 回 413；JSON 最多套 64 层；
   - **跨域**：所有响应都带 `Access-Control-Allow-Origin: *`；`OPTIONS` 请求在进路由之前就回 204 和三条跨域头；
   - 端口先看环境变量 `PORT`，主机看 `HOST`（默认 `0.0.0.0`）；
   - 路径每一段先做百分号解码，写法不对的原样留着；
   - 处理函数没返回时回 204；抛错回 500 并把错误打到标准错误；
   - Go、Java 动集合时加锁（`dbLock sync.Mutex`、`synchronized (DB_LOCK)`）——说明这两种语言是多个请求同时跑的；
   - PHP 每个请求是一个新进程，集合放在 `lc_data.json` 里并加独占锁。

生成的工程里有哪些文件（`target_*.dart`）：Node `server.js` ＋ `lc_runtime.js`（用到语言核心时再加 `lc_lang.js`）；Python `server.py` ＋ `lc_runtime.py`；Go `main.go` ＋ `lc/values.go` ＋ `lc/server.go` ＋ `lc/fetch.go` ＋ `go.mod`；Java `Main.java` ＋ `Lc.java` ＋ `LcJson.java` ＋ `LcServer.java`；PHP `server.php` ＋ `lc_runtime.php` ＋ `lc_json.php` ＋ `lc_data.php` ＋ `lc_server.php`；都带 `README.md`。**没有“库”的位置**——库生成出来的代码放哪，第 4.3 节给了规矩。

### 1.3 现在的校验规则

`lib/lowcode/logic_rules.dart` 一张表管所有编号：G01–G14、P01–P07、S01–S13（合起来 34 条）、L 开头的语言规则、B01–B09 外观规则。后端的在 `backend_validate*.dart`（三个文件共 891 行），页面的在 `logic_validate*.dart`（两个文件共 562 行）。全部是 Dart 写死的，没有“库自己带规则”的入口。

### 1.4 页面逻辑

`logic_blocks.dart`：10 种语句（`setVar changeVar setProp if repeat wait alert navigate log fetch`）、9 种值（`text num bool var prop event bin not join`）；三种事件（`click input load`）；能读的属性 3 个（`text value visible`），能改的 7 个（再加 `bg color src placeholder`）。`logic_js_core.dart` 的 `JsTarget` 是抽象类，读变量 / 写变量 / 读属性 / 写属性四件事由普通网页、Vue、React 三家各自实现——**这四件事就是页面宿主现在实际的“原生接口”**，比第 4 版 6.1 列的 6 个还少，但它是“控件”这一级的，不是 DOM 这一级的。

## 2. 层次定义和判定流程

### 2.1 四层各放什么

| 层 | 放什么 | 不放什么 | 谁写 | 用什么写 |
| --- | --- | --- | --- | --- |
| **L0 宿主原生接口** | 一定要碰外面世界、而且没法用别的 L0 接口拼出来的最小动作：打印、读时钟、取随机、发网络请求、开端口、读写文件、碰页面对象 | 任何“算”的东西；任何能用别的接口加积木拼出来的东西（定时任务、静态文件、路由） | 我们 | 每种语言各一段真代码 |
| **L1 语言核心** | 写法本身：值、变量、运算、流程、函数、类与接口、模块、错误处理、异步、类型 | 任何具体的功能 | 我们 | 语法树 ＋ 生成器 |
| **L2 标准库（小库）** | **纯计算**、而且（a）各语言自带的做法结果不一样、要手写才能逐字节一致，或（b）用积木写太慢：值的规矩、文字、列表、字典、数学、JSON、百分号编码、Base64、哈希、时间的拆分与格式化 | 碰外面世界的（那是 L0）；有业务含义的（那是 L3） | 我们 | 每种语言手写一份，有一致性测试 |
| **L3 库** | 其余一切：路由、中间件、集合、登录校验、页面控件操作、状态管理、组件、表单校验、对接某个框架 | — | 我们（内置库）和用户（用户库），**同一种格式** | L1 的积木 ＋ L2，最底下通过原生绑定碰 L0 或第三方包 |

**和骨架不一样的一处**：第 4 版 6.1 把“JSON 互转、网址的百分号编码”算在“通用宿主接口”里。它们不碰外面的世界，是纯计算，应该归 L2。这样分的好处是 L0 可以真的很小（后端第一批只有 8 个），而且“假宿主”好做（第 11 节）：只要替换 L0，库的其余部分一行不用动就能在测试里跑。

### 2.2 判定流程（来了一个新能力，六个问题）

```
① 它改变的是“怎么写”吗？（新的流程、新的作用域规矩、新的类型写法）
     是 → L1 语言核心。停。
② 它要碰外面的世界吗？（屏幕、网络、文件、时钟、随机、进程、别的程序）
     否 → 跳到 ⑤。
③ 能用已有的 L0 接口加积木拼出来吗？
     能 → L3 库。停。           例：定时任务 ＝ 并发的“开始做” ＋ 睡眠；静态文件 ＝ 路由 ＋ 读文件
④ 拼不出来。那它是所有同类项目都躲不开的最小动作，还是某个产品 / 框架 / 第三方包的功能？
     最小动作 → 新增一个 L0 接口（要过“最小”审查：能不能再拆小？五种语言的标准库都有吗？）。停。
     某个包的功能 → L3 库，带原生绑定和“需要的第三方包”。停。   例：WebSocket、Express、Redis
⑤ （纯计算）用 L1 积木 ＋ 现有 L2 写得出来吗？
     写不出来 → L2。停。         例：按 Unicode 码点切文字、JSON 解析
⑥ 写得出来。那 (a) 各语言结果会不会不一样？ (b) 用积木写会不会慢到不能用？ (c) 是不是几乎每个项目都用？
     (a) 或 (b) 成立 → L2。       例：SHA-256（积木写得出但慢上千倍——推测，没量过）
     都不成立 → L3 库。           例：路径匹配、网址参数拆分、表单校验
     只有 (c) 成立 → 仍然是 L3，做成内置库、默认“用上”。
```

**L2 的门要守紧**：进 L2 的每一个函数都要五种语言各写一份、各自真跑比对（现在 PHP 还没法真跑），成本是 L3 的五倍以上。所以“只是常用”不够格进 L2。

**L0 的“最小”审查**（第 ④ 步里那句）具体问三件事：

1. 去掉它，是不是有一类库彻底写不出来？（是才留）
2. 它能不能拆成更小的接口加一段积木？（能就拆，积木那段进库）
3. 五种第一梯队语言只用标准库都实现得了吗？（实现不了的不能进 L0，只能是“带第三方包的原生库”）

### 2.3 和“特性分四级”的关系

骨架第 2 条的四级里，② 宿主专属和 ③ 原生片段兜底都落在这份文档里：② ＝“只支持某些语言 / 宿主的库”（清单里的 `targets` `hosts`）；③ ＝“只在本项目用的原生绑定”（第 8.6 节）。

## 3. 库的文件格式

### 3.1 决定和理由

| 决定 | 理由 |
| --- | --- |
| 库是一个**文件夹**，分享时打成一个 zip（扩展名 `.lopilib`） | 一个大 JSON 文件在手机上改一处就要整份重写、Agent 也容易写坏；文件夹里每个文件各管一件事，坏了一个别的还能读 |
| 清单里**逐个列出**要读的文件，不靠扫目录 | 导入别人的压缩包时只读清单点了名的文件，多出来的一律不碰；模块的先后顺序也有了着落 |
| 模块文件里“定义”（`decls`）和“积木”（`blocks`）分开 | 一个定义可以有几个外观；也可以有只有定义没有积木的（库内部用的函数） |
| 积木体的存法**沿用现在的** `op` / `e` 写法 | 编辑器、校验、Agent 工具现成能用；库里的定义和项目里的积木是同一种东西 |
| 每个定义、每块积木都有一个**不变的编号**（英文，`id`）和一个可以改的**名字**（可以是中文） | 改名不影响已经用了它的项目（现在“我的积木”已经是这样：`call:f1`） |
| 手写代码**单独成文件**放在 `native/` | 代码塞进 JSON 字符串里满是转义，手机上没法看；单独成文件，导入时的“先看代码”页可以直接显示 |
| 只增字段不改名；不认识的字段**原样留着**，存回去时不丢 | 工程规矩；新版应用做的库拿到旧版应用上打开再存，不能把新字段弄没 |
| 读的时候每个字段先判类型 | 工程规矩（`x is String ? x : 默认`） |

**坏数据怎么读**（三档）：

1. **整个库读不了**（只有这三种情况）：`lib.json` 不是 JSON 对象、`kind` 不是 `lopicode-lib`、`id` 不合规矩。→ 不导入，说明原因；已经在项目里的显示成“坏掉的库”，用到它的积木标 L01，项目照常能开。
2. **某个文件读不了**（模块文件不是 JSON、清单点名的文件不存在）：跳过这个文件，库照常能用，库的卡片上标“有 1 个文件读不了”，里面的积木标 L01。
3. **某一条读不了**（一个定义没有 `id`、一个槽的种类不认识）：跳过这一条或当默认值（不认识的形状当“自动”、不认识的槽种类当“值”——现在 `customBlockLookFromJson` 就是这么做的）。

上限（防坏数据，自定，可改）：一个库最多 64 个模块、一个模块最多 256 个定义和 256 块积木、清单 256KB、单个模块文件 2MB（同 `kBackendMaxFileBytes`）、整个库解压后 8MB、文件数 512。

### 3.2 文件夹结构

```
mini-router/                    文件夹名＝标识的后一段
  lib.json                      清单（必须有）
  modules/
    router.json                 模块（至少一个）
```

### 3.3 清单 `lib.json` 的完整字段表

“坏了怎么办”一列＝字段缺了或类型不对时读成什么。

| 字段 | 类型 | 必填 | 意思 | 坏了怎么办 |
| --- | --- | --- | --- | --- |
| `kind` | 文字，固定 `lopicode-lib` | 是 | 认出“这是一个库” | 不是这个值＝不是库，不读 |
| `format` | 整数，现在是 1 | 是 | 格式版本。只在出现“旧应用读了会理解错”的改动时才加一 | 缺了当 1；比认识的大：照常读认识的字段，卡片上提示“这个库是更新的版本做的，有的内容可能显示不全” |
| `id` | 文字，`作者段/库名`（规矩见 4.1） | 是 | 唯一标识 | 不合规矩＝不读 |
| `name` | 文字，最多 24 字 | 否 | 显示名（可以中文） | 用 `id` 的后一段 |
| `version` | 文字，`大.中.小` | 是 | 版本（规矩见第 5 节） | 当 `0.0.0`，卡片上标“版本号不对” |
| `summary` | 文字，最多 80 字 | 否 | 一句话说明，积木盒和库列表里显示 | 空 |
| `authors` | 列表，每项 `{name, contact?}` | 否 | 作者 | 空表；每项坏的跳过 |
| `license` | 文字 | 否 | 许可证的名字；全文放 `LICENSE.txt` | 空（导出时提醒“没写许可证，别人不知道能不能用”） |
| `homepage` | 文字（网址） | 否 | 主页。只显示，不自动打开、不联网 | 空 |
| `keywords` | 文字列表 | 否 | 搜索用 | 空表 |
| `color` | 文字（颜色键） | 否 | 积木的颜色分类；不认识的回退到 `custom`（现在的做法） | `custom` |
| `icon` | 文字（库里的相对路径） | 否 | 图标文件 | 用默认图标 |
| `hosts` | 列表：`backend` / `browser` / `any` | 否 | 能用在哪种宿主的文档里 | `["any"]` |
| `targets` | 列表：`node` `python` `go` `java` `php` `browser` … | 否 | 作者声明支持的目标语言。**只是声明**；每块积木实际能用在哪些语言，由应用按原生绑定算出来（8.4） | 空表＝“没声明”，全靠算 |
| `needs.host` | 文字列表 | 否 | 用到的宿主原生接口的名字，给人看的（导入时的提示）。应用读库时会**重新算一遍**，以算的为准 | 空表 |
| `needs.std` | 整数 | 否 | 最低需要第几版标准库 | 0；比应用里的新→库不能用，说明“要更新应用” |
| `dependencies` | 字典：库标识 → `大.中` | 否 | 依赖的别的库和最低版本（第 5 节） | 空；坏的条目跳过 |
| `packages` | 字典：目标语言 → 列表，每项 `{name, version, why}` | 否 | 要装的第三方包（8.5） | 空 |
| `native.allowed` | 是否 | 否 | 这个库“允许手写代码”的开关（8.6） | 否。**是“否”时库里的原生绑定一律不生效**（积木变灰） |
| `modules` | 列表，每项 `{file, name}` | 是 | 模块文件，按这个顺序初始化 | 空表＝库里没有东西（能导入，积木盒里是空的） |
| `categories` | 列表，每项 `{id, name}` | 否 | 积木盒里这个库下面的小分组，按这个顺序 | 空表＝不分组 |
| `settings` | 列表，每项 `{id, name, type, default, min?, max?, pattern?, options?, hint?}` | 否 | 库的设置项：每个用了这个库的文档各存一份值（比如端口）（7.6） | 空表 |
| `pickers` | 列表（7.5） | 否 | “清单类的槽”的清单 | 空表 |
| `rules` | 文字（相对路径） | 否 | 规则文件 | 没有规则 |
| `components` | 文字列表（相对路径） | 否 | 组件文件 | 空表 |
| `tests` / `examples` | 文字列表（相对路径） | 否 | 用例 / 示例文件 | 空表 |
| `docs` | `{readme, blocks}` | 否 | 说明文档在哪 | 没有文档 |
| `legacyOps` | 字典：旧 op 名 → 积木编号 | 否 | 旧名对照表：旧文档里的 `respondJson` 是这个库的哪块积木（第 12 节）。格式上谁都能写，但**只有内置库的才生效**（否则一个导入的库能冒名顶替旧积木） | 空 |
| `autoUse` | 列表：`backend` / `page` | 否 | 哪种文档自动“用上”它。同样只有内置库的生效 | 空表 |
| `origin` | `{id, version}` | 否 | “复制一份来改”时记下是从哪个库的哪一版复制的 | 没有 |
| `files` | 字典：相对路径 → SHA-256 | 否 | 导出时写的每个文件的校验值；导入时对不上就提示“导出以后被改过”。**不是安全措施**（改的人可以连校验值一起改），只防传坏 | 空＝不核对 |

以后要加的东西（多语言文案、截图、最低应用版本……）一律加新字段。

### 3.4 一个写全了的示例库：`demo/mini-router`（小路由）

- 五份 JSON 文件都用 `python3 -c "json.load(...)"` 读过，是合法的 JSON；规则文件里的三条正则在本机 Python 里试过（`/`、`/hello/:name` 通过，`hello`、`/a//b`、`/a/` 不通过；`/a/:id` 和 `/a/:x` 归一化后相同）。

- `decls` 里 `visibility` 是 `module` 的（路由表、登记、对得上、分发）外面看不见；`回应` 和 `生成编号` 是公开的。
- `blocks` 里：`onRoute` 指向不公开的函数 `add`——**函数不公开，积木公开**，用户只能通过这顶帽子登记路由；`reply` 是收尾型；`pathParam` 没有对应的函数（`"of": "@index"`），它是**调用处展开**的：`expand` 里 `context` 取“所在的那顶 `onRoute` 帽子的参数『请求』”，`slot` 取这块积木自己槽里选的名字。

## 4. 命名空间与重名

### 4.1 库的唯一标识怎么起

**决定**：`作者段/库名`，两段，中间一个斜杠。

- 每段：小写英文字母开头，只用小写字母、数字、连字符；不许连着两个连字符，不许以连字符结尾。作者段 2–32 个字符，库名 2–48 个字符。
- 留给我们自己的作者段：`lopi`（内置库，例如 `lopi/http-service`、`lopi/page`）和 `local`（项目自己的隐含库，见 12.3）。导入的库用这两个作者段一律拒绝。
- 用户第一次新建库时填一次“我的署名”（就是作者段），以后新建的库默认用它。**不用注册、不联网、不保证全世界唯一**——没有商店就没有谁来保证，真撞了在导入时处理（见 10.4）。
- 显示名（`name`）另外存，可以是中文，可以重复。列表里显示名下面用小字带上标识。

**别人是怎么起的**（都对官方文档核对过，来源见文末），学什么、不学什么：

| | 它的规矩 | 学 | 不学 |
| --- | --- | --- | --- |
| npm | 名字连作用域最多 214 个字符；新包不许有大写字母；名字会进网址、命令行、文件夹名，所以不能有网址里不安全的字符；可以带作用域前缀，如 `@myorg/mypackage` | “名字会变成文件夹名，所以只许安全字符”；两段式（作用域/包名） | `@` 前缀（多一个符号，手机上难打） |
| PyPI | 名字只许英文字母、数字、点、下划线、连字符，首尾是字母或数字；比较前要“规范化”：全部小写，连着的 `.` `-` `_` 换成一个 `-` | “`Friendly-Bard` 和 `friendly_bard` 算同一个”这个教训 | 我们干脆**只许小写和连字符**，就不需要规范化这一步了 |
| Go 模块 | 模块路径既说它是什么、也说去哪找它（仓库路径＋子目录）；大版本 2 以上必须在路径最后带 `/v2` 这样的后缀，不同大版本当成不相干的两个模块，可以同时用 | “不兼容的大改＝换一个名字”（见 5.3） | 路径即网址（我们没有托管，库是文件传的） |
| Maven | 三样合起来唯一：`groupId`（建议用自己控制的域名倒过来写）、`artifactId`（小写字母、数字、连字符）、`version` | `artifactId` 的字符规矩 | 倒写域名（用户没有域名） |
| Composer | `vendor/project`，必须小写，词之间用 `-` `.` `_`；vendor 必填，官方建议拿不准就用自己的 GitHub 用户名 | **整个照这个思路**：两段、小写、作者段必填、没有中心登记也能用 | 允许 `.` 和 `_`（少一种写法少一种混淆） |

### 4.2 两个库都有“回应”积木怎么办

**不冲突，因为积木不是靠名字认的。**

- 文档里存的是 `库标识#积木编号`：`{"op": "demo/mini-router#reply", …}`。名字（“回应”）只是画在积木上的字。
- 积木盒：每个“用上”的库一个分类（页签），名字和颜色是库自己的。两块“回应”各在各的页签里。
- 搜索结果、问题清单、Agent 工具的返回：写成“回应（小路由）”。
- 画布上：积木的颜色跟库走；按住积木的小菜单第一行显示“来自：小路由 1.2.0”。**只有当项目里真的有两块文案一模一样的积木来自不同的库时**，才在积木左上角加一个库图标的小角标——平时不加，免得画布花。
- 旧文档里不带库标识的 op（`respondJson`）＝内置库“旧名对照表”里的那一块（12.1）。

**库里面的重名**（新增规则，K 开头＝库）：

| 号 | 级别 | 内容 |
| --- | --- | --- |
| K01 | 错误 | 同一个库里两块积木编号相同；同一个模块里两个定义编号相同 |
| K02 | 错误 | 同一个模块里两个定义名字相同（忽略大小写——PHP 的函数名不分大小写，这是第 2 阶段已有的规矩） |
| K03 | 警告 | 同一个库里两块公开积木的文案模板一模一样（用的人分不清） |

### 4.3 库里的名字在生成的代码里叫什么

**决定**：

1. 每个“用上”的库在项目里有一个**代号**：取标识的后一段，连字符换成下划线（`mini-router` → `mini_router`）。项目里两个库代号相同时，后来的那个改用“作者段_库名”。代号记在项目的库清单里（5.4），定了就不变——否则加一个库会让别的库生成的代码全部改名。
2. 定义用它的**编号**（`id`，英文）生成名字，不用显示名。所以库作者改中文名，生成的代码不变。
3. 沿用现在的前缀：函数 `f_编号`、模块级变量 `g_编号`、原生绑定的包装函数 `n_编号`、类 `C_编号`。

| 语言 | 库的代码放哪 | 从外面怎么叫公开函数 `reply` | 说明 |
| --- | --- | --- | --- |
| Node | `lib/mini_router/router.js`（一个模块一个文件） | `L_mini_router.f_reply(…)`（文件头 `const L_mini_router = require("./lib/mini_router/router.js")`） | 和现在 `const lc = require("./lc_runtime.js")` 同一个路子 |
| Python | `lib_mini_router/router.py` | `L_mini_router.f_reply(…)`（`from lib_mini_router import router as L_mini_router`） | 一个库多个模块时别名带上模块名 |
| Go | `lib/mini_router/*.go`，一个库一个包 | `L_mini_router.F_reply(…)` | **公开的名字必须大写开头**：`F_reply` 外面能用，`f_hidden` 外面用不了。**本机跑过**（Go 1.25）：一个两包的小程序，调 `F_reply` 打出 201，改成调 `f_hidden` 编译报 `name f_hidden not exported by package mini_router`。所以 Go 里“公开 / 不公开”直接落在首字母上 |
| Java | `L_mini_router_router.java`，一个模块一个类，都是静态方法 | `L_mini_router_router.f_reply(…)` | 现在生成的 Java 都在默认包里（`Main.java` `Lc.java`），先照旧不分包 |
| PHP | `lib_mini_router_router.php` | `l_mini_router_router_f_reply(…)` | PHP 的函数是全局的，只能靠前缀隔开。**PHP 一概没跑过**（本机没有 PHP） |

以上是**提议的形状**：现在没有生成库的代码，除了 Go 那一项以外都没跑过；模块之间互相引用时各语言的导入写法、会不会绕圈，要等语言核心的“模块”那部分定了再对。

**“看代码”里好不好读**：编号是作者起的。新建定义时编号默认是 `f1` `f2`（现在的做法）；库导出时检查公开的定义，编号还是 `f数字` 的提醒一句“给它起个英文编号，别人看生成的代码时好懂”，不拦。

## 5. 版本与依赖

### 5.1 版本号

**决定**：三段数字 `大.中.小`，照语义化版本 2.0.0 的主干（对 semver.org 核对过）：

- 三段都是不带前导 0 的非负整数；
- 做了**不兼容**的改动，大版本加一，后两段归零；
- **加了功能但旧的照常能用**，中版本加一，小版本归零；
- **只修问题**，小版本加一；
- 大版本是 0（`0.y.z`）表示还在试，什么都可能变。

**不做**预发布后缀（`1.0.0-beta.1`）和构建信息（`+build5`）：手机上讲不清，也没有发布渠道需要它。读到带后缀的版本号：只认前面三段数字，后缀原样留着不丢。

**“不兼容”对积木来说具体指什么**（应用自己会算，见 5.5）：公开的积木被删、槽被删、加了没有默认值的槽、槽的种类变了、形状变了（语句变成值）、公开函数的参数少了或顺序变了。

### 5.2 库依赖库

- 清单里写 `"dependencies": {"lopi/http-service": "1.2"}`，意思只有一种：**至少 1.2.0，并且大版本还是 1**。不做别的范围写法（`~` `>=` `||` 都不做）——一种写法，手机上一句话说得清：“要‘接口服务’1.2 或更新的 1.x”。
- 依赖最多套 8 层；绕圈（A 依赖 B、B 依赖 A）＝错误（L10 的库版本）。
- “用上”一个库时，它依赖的库一起复制进项目；项目里已经有、版本够的就不动；版本不够的问“要把『接口服务』从 1.1.0 换成 1.3.0 吗”，列出变化（5.5）。

### 5.3 依赖冲突

**决定：一个项目里，一个库只留一个版本。**

| 情况 | 怎么办 |
| --- | --- |
| 两个库要同一个库的同一个大版本，最低要求不同（A 要 1.2，B 要 1.4） | 用高的那个（≥1.4 的 1.x）。照语义化版本，1.4 对 1.2 是兼容的 |
| 两个库要同一个库的**不同大版本**（A 要 1.x，B 要 2.x） | **拦下来**，不“用上”后来的那个，说清楚：“『登录校验』要『接口服务』2.x，可是项目里的『小后台』要 1.x。两个只能留一个。”给两个出路：看看『小后台』有没有新版 / 不用『登录校验』 |
| 项目自己直接用的版本比某个库要求的低 | 提示更新（同 5.2） |

**为什么不做“两版并存”**：并存意味着积木盒里出现两个“接口服务”、同一块积木有两个来历、生成的代码里两份路由表各管各的——用户根本分不清请求进了哪一份。Go 允许并存，靠的是“大版本不同＝名字不同＝两个不相干的模块”。我们学它的**前一半**：库作者要做不兼容的大改时，**建议换一个标识**（`me/router` → `me/router2`），两个标识当然可以同时用，而且名字不同，用户一眼分得清。导出时如果算出来“这次是不兼容的改动”，就在这里给这个建议。

### 5.4 项目里记录用的是哪一版

项目里一个文件 `blocks/libs.json`：

```json
{"format": 1, "libs": [
  {"id": "demo/mini-router", "version": "1.2.0", "alias": "mini_router", "from": "file", "sum": "（清单文件的 SHA-256）"},
  {"id": "lopi/http-service", "version": "1.0.0", "alias": "http_service", "from": "builtin"}
]}
```

- `from`：`builtin`（内置，不复制）、`mine`（从应用级“我的库”复制来的）、`file`（从文件导入的）、`project`（就在项目里新建的）。
- 除内置库以外，库的文件夹整个在项目的 `blocks/作者段/库名/` 里（第 4 版 5.4 已定：项目才能脱离手机单独存在）。
- **内置库不复制**，只记版本：它跟着应用走。应用更新后内置库版本变了，打开项目时如果大版本变了才提示；中、小版本变了不打扰（内置库的兼容由我们的一致性测试保证，12.2）。
- 每份积木文档自己记“用上了哪些库”（`uses`，见示例的 `examples/hello.json`）和这些库的设置值；`blocks/libs.json` 记的是整个项目里有哪些库、各是哪一版。
- 写用 `writeJsonAtomic`、读用 `readJsonFile`（工程规矩）；坏了：当成“项目里没有登记任何库”，然后按 `blocks/` 下面实际有的文件夹重建，不崩。

### 5.5 库更新以后，“参数变了”的提示

换版本之前，应用拿新旧两版的**公开部分**逐项比，只列和这个项目有关的（项目里用到的积木）：

```
把“小路由”从 1.2.0 换成 2.0.0

会坏掉的（3 处在用）
  · “回应”少了一格“状态”        2 处，这一格里的内容会丢
  · “路径参数”没有了            1 处，会变成“不认识的积木”

会自己补上的
  · “当收到”多了一格“说明”      新格子里先放默认值（空）

没有影响的：另外 5 块积木没变

[ 先不换 ]   [ 换，并帮我改 ]
```

- “帮我改”用的就是现成的 `remapCallArgs`（参数增删改名换序后各处调用跟着变、丢掉的内容列清单）。换完可以撤销。
- 比对的依据是积木编号和槽名，所以库作者只改了显示的文案不算变化。
- 作者这一头：导出时应用自己比“上一次导出的公开部分”和现在的，算出是不兼容 / 加功能 / 没变，**版本号加得不够就提醒**（“这次删了一块公开积木，别人更新后会坏，建议版本改成 2.0.0”），不拦。上一次导出的公开部分存在应用级“我的库”里那个库的 `.export/` 下。

## 6. 导入导出与可见性

### 6.1 可见性三档

| 档 | 谁能用 | 默认 |
| --- | --- | --- |
| **模块内** | 只有同一个模块里的定义 | 新建的定义默认是这一档 |
| **库内** | 同一个库的所有模块 | 只有库里有两个以上模块时，菜单里才出现这一档 |
| **公开** | “用上”这个库的项目和别的库 | 要手动打开 |

- 定义（函数、类、常量、类型）和积木（外观）**各有各的可见性**。常见的搭配是“函数不公开、积木公开”（示例里的 `onRoute`）：用户只能按积木规定的样子用。
- 公开的积木指向的定义不要求公开；但公开的函数的参数类型、返回类型里出现的类 / 记录 / 枚举必须公开（否则别人拿到一个说不出类型的值）——规则 K04（错误）。
- 类的成员另有“公开 / 私有”，那是语言核心的事（L11 已经管“在类外面读写私有字段”）。

### 6.2 库能公开什么

函数、类、接口、常量、类型（记录 / 别名 / 枚举）、积木外观、组件、清单（7.5）。**模块级变量不能公开**（只能通过函数读写）：公开一个可以随便改的变量，等于把库的内部状态交给所有人改，出了问题没法查；各语言跨模块改变量的写法也不一样。

### 6.3 项目“用上”一个库以后，积木盒里出现什么

| 库里有 | 出现在哪 |
| --- | --- |
| 公开的积木 | 积木盒多一个分类，名字和颜色是库的；里面按 `categories` 分小组 |
| 公开的函数，但没有给它做积木 | 自动给一块默认外观的积木（“名字 ＋ 每个参数一个槽”，现在 `defaultLookTemplate` 就是这么做的），放在库分类的最后一组“其它” |
| 公开的类 | “新的 [类名]”一块值积木；每个公开方法一块（“让 {对象} 做 …”/“{对象} 的 …”）；每个公开字段的读、写各一块。作者可以给其中任何一块另做外观替掉默认的 |
| 公开的常量 | 一块值积木 |
| 公开的枚举 | 出现在“固定选项”槽的来源里，也有一块“[枚举▾] 的 [某一项▾]”值积木 |
| 公开的类型（记录、接口、类） | 出现在所有“选类型”的地方（参数类型、变量类型） |
| 公开的组件 | 页面编辑器的控件面板多一组，名字是库的（只在页面文档里） |
| 清单 | “变量与集合”那个面板多一栏，名字是清单的（7.5） |
| 设置项 | 文档的“设置”面板多一节，名字是库的（7.6） |
| 规则 | 不显示；违反了才在积木上出红点 |
| 示例、文档 | 库分类最上面一行“说明 · 示例”；按住任何一块积木 →“这块怎么用” |

**不公开的东西一概不出现**，但“看里面”（只读地打开库）能看到。

## 7. 库里能放什么

### 7.1 总表

| 东西 | 存在哪 | 这一轮的状态 |
| --- | --- | --- |
| 函数 | 模块的 `decls`，`kind: func` | 语言核心已有（`LFuncDecl`） |
| 模块级变量 / 常量 | `kind: var` / `const` | 节点已有（`LVarDecl`），后端页还没接；**库必须要它**（路由表、计数器都是） |
| 类、接口 | `kind: class` / `interface` | 节点已有，没实现（第 5 阶段） |
| 枚举、记录、类型别名 | `kind: enum` / `record` / `alias` | 归类型部分的同事定；这里只留位置 |
| 原生绑定 | `kind: native` | 第 8 节 |
| 积木外观 | 模块的 `blocks` | 7.2、7.3 |
| 组件（前端） | `components/*.json` | 格式归 D；库这一层只管“它有编号、可见性、属于哪个库” |
| 校验规则 | `rules.json` | 7.4 |
| 清单 | `lib.json` 的 `pickers` | 7.5 |
| 设置项 | `lib.json` 的 `settings` | 7.6 |
| “最后启动” | 模块的 `start` | 7.7 |
| 用例、示例、文档、图标、许可证 | 各自的文件 | 第 11 节、3.2 |

### 7.2 积木外观

沿用 `CustomBlockLook`（名字、形状、文案模板、槽表、颜色键、说明），在它外面包一层：

```json
{"id": "onRoute", "of": "add", "category": "route", "visibility": "public",
 "look": { …CustomBlockLook… },
 "preset": {"方式": "GET"},
 "context": {"请求": {"hat": "onRoute", "param": "请求"}},
 "expand": { …式子或语句… },
 "deprecated": {"since": "1.3.0", "use": "onRoute2"}}
```

| 字段 | 意思 |
| --- | --- |
| `of` | 这块积木背后是哪个定义：函数编号；`类编号.方法编号`；`类编号.new`（构造）；`@…` 开头＝没有定义，全靠 `expand` |
| `preset` | **预先填死的参数**：这些参数不出现在积木上。同一个函数可以做成好几块积木（“当收到 GET …”“当收到 POST …”） |
| `context` | **隐含的上下文参数**：这个参数不出现在积木上，值取自“所在的那顶帽子的某个参数小块”。现有的“路径参数”“请求头”“输入的内容”都是这种：积木上没有“请求”那一格，可它要用这次的请求 |
| `expand` | **调用处展开**（7.3） |
| `deprecated` | 这块已经不建议用：积木盒里不再出现，已经用了的照常能用，按住时提示“换成…” |

**形状**（六种，和 `CustomBlockShape` 一致）：自动 / 语句 / 值 / 是否 / 收尾 / 帽子。

**槽的种类**（现有五种，库需要再加四种）：

| 种类 | 存盘名 | 有没有 | 说明 |
| --- | --- | --- | --- |
| 值 | `value` | 有 | 可以再标 `literalOnly`（只许直接填，不许放值积木——帽子上的路径要在生成前就知道）和类型 |
| 是否 | `boolean` | 有 | |
| 固定选项 | `choice` | 有 | 选项可以来自一个公开的枚举 |
| 内联口 | `inlineMouth` | 占位 | 7.3 |
| 回调口 | `callbackMouth` | 占位 | 带 `params`：回调的参数名，画成口上的参数小块 |
| **从清单里选** | `picker` | **新** | `picker` 指向一个清单（7.5） |
| **变量（写入目标）** | `assign` | **新** | 槽里选一个变量，积木把结果写进去；可以标 `optional`。现有的“加好的那条放进变量”“结果放进变量”就是这种。只能用在调用处展开的积木上 |
| **新名字** | `binder` | **新** | 槽里起一个名字，在口里面当变量用（“对每一项 [x]”的那个 x）。只能用在带内联口的积木上 |
| **类型** | `type` | **新** | 槽里选一个类型（“新的 [类型▾] 列表”）。归类型部分定，这里只留名字 |

### 7.3 两种积木：调用型和展开型

**调用型**（绝大多数）：生成代码时就是一次函数调用。回调口里的积木包成一个匿名函数当参数传进去。

**展开型**：生成之前，把这块积木**原地换成** `expand` 里写的那一段（式子或几句语句），槽里的东西填进对应的位置。只有下面四种情况需要它，别的一律做成调用型：

| 需要展开的原因 | 例子 |
| --- | --- |
| 有**内联口**（口里的“返回”“跳出”要作用于外面） | 现有的“请求别的网址（成功后 / 失败后）”：口里要能放“返回数据” |
| 有**写入目标槽**或**新名字槽**（函数没法替调用的人给变量赋值） | “往集合里加一条，加好的那条放进变量 [x]” |
| 有**隐含的上下文参数** | “路径参数 [name]” |
| **收尾型**（`回应 …` → `返回 回应(…)`）和**帽子型**（下面那一串包成函数，传给登记函数） | 这两种的展开规则是固定的，作者不用写 `expand` |

展开型的规矩（校验拦）：

- 不许递归（展开会停不下来）——规则 K05；第 2 阶段已经留了 `LFuncInfo.recursive`。
- `expand` 里只能出现：这个库自己的定义（按编号）、标准库、核心积木、`{"e": "slot"}`（槽里的东西）、`{"e": "context"}`（上下文参数）、`{"e": "setting"}`（设置项）。不能出现用户文档里的名字。
- `expand` 里新建的变量，展开时自动改成不会撞的名字（第 4 版 5.2 已定）。
- 同一个槽在 `expand` 里出现两次：先存进临时值、只算一次（免得槽里的东西被算两遍）。

**为什么不干脆都做成展开型**：展开型的每一处使用都会把那段代码抄一遍，生成的代码又长又难读；出错时也指不到“是哪个函数里出的错”。

### 7.4 校验规则

**四种声明式的**（不用写代码，库作者在“规则”页里选和填）：

| 种类 | `kind` | 能说什么 | 34 条里对应的 |
| --- | --- | --- | --- |
| **槽约束** | `slot` | 某个槽：必填、数字范围、是不是整数、正则、长度、必须是清单里有的 | G14、P01、P02、S04、S05、S06、S13（S01 端口归设置项自带的范围检查，S03 集合名归清单的名字规矩） |
| **位置约束** | `place` | 某块积木：只能在某种帽子下面 / 不能在回调口或匿名函数里面 / 一顶帽子下面最多几块 | P05；“返回响应不能放在自定义积木里”（L15 的库版本） |
| **唯一约束** | `unique` | 同一份文档里，某种积木的某几个槽合起来不许重复；比之前可以先做几条正则替换（`normalize`） | P07、S07 |
| **槽间约束**（新加） | `relate` | 一个槽能填什么，取决于同一块积木（或它所在帽子）的另一个槽填了什么 | P03（“内容变化”只能挂在输入框上）、P06（这种控件没有这个属性）、S09（取了路径里没有的参数——示例里用“从帽子的槽里提取的清单”做的） |

**声明不出来、要算的规则**：34 条里只有 **S08“接口被前面的挡住”**（要拿两条路径逐段比）。

**决定**：应用里放一小批**有名字的检查器**（Dart 写的，现在只需要 `routeShadow` 一个），库在规则文件里按名字引用，并说明哪个槽对应检查器要的哪个参数（示例 `rules.json` 的 R05）。内置库和用户库**都能引用**，**都不能新写**。

理由和代价：

- 好处：格式上内置库和用户库仍然是同一种；用户自己做的路由库也能用上“被挡住”的检查。
- 代价：这是“除了语言基础和标准库以外都用积木封装”的一个**例外**——检查器不是积木搭的。要彻底没有例外，应用里得有一个**能直接执行积木的解释器**（现在积木只能生成代码、拿到别的地方去跑，应用自己不会跑）。那是一件大事（要用 Dart 把标准库再写一遍并保证逐字节一致），这一轮不建议做，记成 GAP-C-10。
- 库自带规则的编号在库内自己编（`R01`…），显示时带上库的代号（“小路由·R02”），不占用 G / P / S / L / B / K。内置库的规则**保留原来的编号**（S07 还叫 S07），因为用户见过。

级别：`error`（拦生成 / 导出 / 运行）或 `warning`（不拦），和现在一样。规则文件坏了：坏的那一条跳过；整份读不了就当没有规则，不崩。

### 7.5 清单类的槽（“从某一类东西里选”）

一个清单＝“一类有名字的东西”。库在清单里声明它，槽用 `picker` 指向它。清单里的东西从哪来，有三种：

| 来源 | `source` | 东西存在哪 | 例子 |
| --- | --- | --- | --- |
| **文档里存的** | `document` | 用了这个库的那份文档里，`libData` 下面按库标识分开存 | 数据集合：用户在面板里加“todos”“users” |
| **宿主给的** | `host` | 不存；宿主现算 | 页面上的控件（每个带类型：按钮 / 输入框 / 文本…）、文档里的变量 |
| **从别的槽里提取的** | `slot` | 不存；现算 | 路径参数：从所在帽子的“路径”槽里用正则提出 `:名字` |

`document` 清单的声明：

```json
{"id": "collections", "name": "数据集合", "itemName": "集合", "source": "document",
 "namePattern": "^[A-Za-z][A-Za-z0-9_]{0,31}$", "max": 64,
 "fields": [{"id": "note", "name": "说明", "type": "文字"}],
 "legacyKey": "collections"}
```

- 管理界面是**通用的一页**（加、改名、删；改名时用到它的槽跟着改；删之前说“有 N 处在用”），库不用自己画界面。
- `legacyKey`：旧文档里这个清单存在顶层的哪个键下面（后端的 `collections`）。读的时候认旧位置，不改就不重写文件。只有内置库的生效。
- 运行时库怎么拿到这张清单：`{"e": "pickerItems", "picker": "collections"}` 生成成一个写死的列表（集合名在生成时就知道）。

### 7.6 库的设置项

有的库要用户给几个值才能工作：端口、基础网址、是否打印请求日志。**这不是积木**（它不在某一串里），所以单独一类。

- 声明在清单的 `settings`：编号、名字、类型（整数 / 小数 / 文字 / 是否 / 固定选项）、默认值、范围或正则、一句说明。
- 值存在用了这个库的那份文档里（`settings: {"库标识": {"port": 8080}}`）；旧文档顶层的 `port` 由内置库的对照表认。
- 界面：文档“设置”面板里每个库一节，一行一项。
- 库里用 `{"e": "setting", "id": "port"}` 读，生成成字面量。
- **密钥不放这里**（Key、密码）：设置项会进存盘文件和生成的代码。密钥走环境变量（`sys.env`，9.1），库的说明里写“要设哪个环境变量”。

### 7.7 库的三个时刻

一份文档生成的程序，启动时按这个顺序跑：

```
① 每个用上的库，按依赖顺序：模块级变量初始化 → 模块的 init（库自己的准备工作）
② 用户文档：模块级变量初始化（按画布上从上到下的顺序）
③ 用户文档：每顶帽子的“登记”（按画布顺序——路由先后就是这个顺序）
④ 用户文档：“启动时”那一串
⑤ 每个用上的库，按依赖的反顺序：模块的 start（“最后启动”）——“接口服务”在这里开端口
```

为什么要有 ⑤：开端口必须在所有帽子登记完之后；现在这件事是生成器写死的（`lc.start(端口)` 写在文件最后）。改成库以后，库得有地方说“等用户的都弄完了再做这件事”。用户也可以不要自动的：文档设置里点“显示启动积木”，⑤ 就变成画布上看得见的一串（第 4 版 8.1 已定）。

### 7.8 组件库和 JS 库

- **组件库**＝带组件的库，`hosts` 是 `["browser"]`。一个组件在库这一层要有：编号、名字、可见性、属性表（带类型和默认值）、插槽、它会发出的事件、一棵控件树、样式、以及它自己的一个逻辑模块（组件的行为用积木写在库的模块里）。现在的 `LcComponentDef` 只有“属性表（四种类型）＋控件树”，缺插槽、事件、自己的逻辑——**具体格式由 D 定**，这里只要求它能放进库的 `components/` 里、遵守同一套标识 / 版本 / 可见性 / 依赖规矩。
- **JS 库**＝`hosts` 是 `["browser"]`、没有组件、只有函数 / 类 / 积木的库（比如“本地存储”“表单校验”“定时器”）。和后端库没有任何格式上的区别。
- 一个库可以同时有后端和页面两部分吗？**不做**：一份文档只属于一种宿主，混在一起的库里总有一半积木是灰的。前后端共用的纯计算（表单校验规则）做成 `hosts: ["any"]` 的库。

## 8. 原生绑定

### 8.1 怎么声明

原生绑定是模块里的一种定义（`kind: native`）：**一个签名 ＋ 每种目标语言一段函数体**。

```json
{"kind": "native", "id": "newId", "name": "生成编号", "visibility": "public",
 "params": [], "returns": "文字",
 "waits": false, "fails": false, "pure": false,
 "doc": "一个随机的 36 个字符的编号。",
 "impl": {
   "node":   {"head": ["const crypto = require(\"node:crypto\");"], "body": "native/newId.node.js"},
   "python": {"head": ["import uuid"], "body": "native/newId.python.py"},
   "java":   {"head": [], "body": "native/newId.java.java"}
 }}
```

| 字段 | 意思 |
| --- | --- |
| `params` | 参数：名字、类型、默认值。和函数的参数是同一种写法 |
| `returns` | 返回类型；没有返回值写 `空` |
| `waits` | **要不要等**：是＝它要过一会儿才有结果（网络、文件、睡眠）。生成器按各语言的写法处理（Node 里是 `await`，同步的语言里直接等）。具体怎么等归“异步”那部分定 |
| `fails` | **会不会出错**：是＝它可能抛错。手写代码里出错必须用小库给的办法抛（各语言一个函数，消息是文字），这样“试着做”接得住，五种语言报的话才能一样 |
| `pure` | 是＝不碰外面的世界、同样的输入一定同样的输出。只有标了“是”的才参加“逐字节比对”的用例；没标的用例只能写“检查”（长度、类型） |
| `impl` | 每种目标语言：`head`（要放在文件头的导入行，原样写；几个绑定重复的行只留一份）、`body`（函数体文件的相对路径）、可选 `files`（要原样带进工程的附带文件） |

宿主原生接口（L0）用**同一种声明**，只是它们的实现在应用里（各语言的运行时小库），不在库的文件夹里；库里用 `{"e": "host", "name": "http.serve", "args": […]}` 调，不用自己声明。

### 8.2 生成出来长什么样

**决定：每个原生绑定在每种语言里一律生成成一个包装函数，函数体就是那个文件的内容；用到它的地方是普通的函数调用。**

```js
// lib/mini_router/native.js（生成的）
const crypto = require("node:crypto");          // ← head
function n_newId() {                            // ← 生成器写的函数头
  return crypto.randomUUID();                   // ← native/newId.node.js 的内容，原样
}
module.exports = { n_newId };
```

为什么不用“代码模板，参数原地替换”（Blockly 的生成函数就是拼字符串）：

- 原地替换要操心运算的先后、参数被算两遍、参数里有逗号引号——手写代码的人很容易写错，而且错得很隐蔽。
- 包成函数以后，手写的那一段**只看得到自己的参数名**，生成器不需要看懂它。
- 代价：多一层函数调用。可以接受。

**值怎么过这道边界**（手写代码的人必须知道的约定）：

- 参数标了 `文字` / `数字` / `是否` 的：进函数之前生成器已经转好了，手写代码拿到的是那种语言自己的字符串 / 数 / 布尔。
- 参数标了 `列表` / `字典` / `任意`，或没标的：拿到的是小库的值（Go 里是 `any`，列表是 `*lc.List`；PHP 里是 `LcList` / `LcObj`；Node 和 Python 里基本就是原生的数组和字典）。要当原生的用，调小库给的两个转换函数（“转成原生的”“从原生的转回来”）。**这两个转换函数现在小库里没有对外给出来，要加**（GAP-C-11）。
- 返回值同理：标了类型的由生成器转回小库的值。
- 回调（参数类型是 `函数`）：拿到的是小库的函数值，要用小库的“调用”去调（现在的 `lc.call`），不能直接当原生函数调。

### 8.3 每种语言的实现放哪

| 语言 | 函数体文件 | 生成器把它放进 | `head` 是什么 |
| --- | --- | --- | --- |
| Node | `native/<编号>.node.js` | `lib/<代号>/native.js` 里的一个函数 | `require` 行 |
| Python | `native/<编号>.python.py` | `lib_<代号>/native.py` 里的一个函数（函数体按缩进放进去） | `import` 行 |
| Go | `native/<编号>.go.go` | `lib/<代号>/native.go` 里的一个函数 | 导入的包路径 |
| Java | `native/<编号>.java.java` | `L_<代号>_native.java` 里的一个静态方法 | `import` 行 |
| PHP | `native/<编号>.php.php` | `lib_<代号>_native.php` 里的一个函数 | `require` / `use` 行 |
| 浏览器 JS | `native/<编号>.browser.js` | 页面脚本里的一个函数 | 没有（浏览器里没有 `require`） |

文件名里第二段是目标语言，第三段是扩展名（为了手机上的代码查看器能认出语言上色）。**以上是提议的形状，没有生成器、没跑过**；Python 的缩进、Go 的“导入了没用到会编译不过”这类细节，实现时要逐个语言真跑。

### 8.4 某种语言没有实现：积木怎么变灰

- 读库的时候算一次：**每块公开积木能用在哪些语言** ＝ 它背后的定义沿着调用关系往下走，碰到的所有原生绑定都有实现的那些语言。只要链条上有一个原生绑定没有某种语言的实现，这块积木在那种语言下就用不了。
- 清单里 `native.allowed` 是“否”的库：所有原生绑定当作“哪种语言都没有实现”。
- 界面：当前文档选的语言下用不了的积木，在积木盒里是灰的，按住显示原因——“这块在 Go 里用不了：它用到的‘生成编号’没有 Go 的写法”。已经在画布上的标 L06（错误，拦生成）。换一种语言，灰的可能就亮了。
- 清单里的 `targets` 只是作者的声明：算出来比声明的少，导出时提醒作者（“你说支持 Go，可是‘生成编号’没有 Go 的实现”）。

### 8.5 需要第三方包

清单里声明：

```json
"packages": {
  "node":   [{"name": "express", "version": "^4.19.0", "why": "路由和服务"}],
  "python": [{"name": "fastapi", "version": ">=0.110"}, {"name": "uvicorn", "version": ">=0.29"}]
}
```

- `version` 的写法是**那种语言的包管理器自己的写法**，原样写进生成工程的依赖文件（Node 的 `package.json`、Python 的 `requirements.txt`、Go 的 `go.mod`、PHP 的 `composer.json`）。几个库要同一个包、版本写法不同：不替它们算，直接说“『甲库』和『乙库』对 express 的版本要求不一样”，让用户选留哪个库。
- “运行”前检查：沿用现在后端“点运行以后替她配工具”的那一段（`backendRunProvider`：等环境 / 核对 / 等她点头 / 正在装 / 没装成）。要装包＝要联网，**先问**，问的时候列出包名、版本、是哪个库要的。装不成写清真正的原因（工程规矩）。
- 没有第三方包的库，库的卡片上标“零依赖”。
- **Java 的第三方包这一轮不建议做**：要 Maven 或 Gradle，第 4 版调研过完整 Gradle 约 2GB，手机上太重。Java 下带第三方包的库＝灰的，原因写“Java 下还不能装第三方包”。（需要霜霜拍板，见文末。）
- **五种语言各自“怎么查装没装、怎么装”的命令我没有核对**，实现时对着各包管理器的官方文档核对后记进 `docs/api-notes.md`（工程规矩）。

### 8.6 用户库能不能写原生绑定；“原生片段”

**决定：能，但默认关着，而且“原生片段”不另设一套机制。**

为什么要允许：霜霜要的是“用户能自己写库”。一个不能碰任何新东西的库体系，用户只能在我们给的 L0 上打转；想接一个第三方包、想用一个标准库里我们没包的函数，都做不了。MakeCode 的扩展正是“积木 ＋ 包 ＋ 手写的底层实现”三样齐全才成气候的。

要防的事和对应的办法：

| 担心 | 办法 |
| --- | --- |
| 手写代码**不检查**：写错了、各语言行为不一样、根本编译不过 | 积木角上一个“手写”小标记（它自己是原生绑定，或者它用到的定义里有用户写的原生绑定）；库的卡片上写“含手写代码 N 段 · 没有经过检查”；“看代码”里手写的那几行有底色。**不承诺**五种语言一致 |
| 手写代码**可能有危险操作**（删文件、把密钥发到外面） | 它只在用户点“运行”时、在运行环境里跑，**永远不在应用自己的进程里跑**——风险和“让 Agent 在终端里跑一段命令”是同一级的，不是新的一级。导入时的处理见 10.4 |
| **Agent 也能写** | Agent 的库工具里，“写原生绑定的函数体”这一个动作单独过确认卡（卡上显示完整的代码），和现在“执行命令要确认”一个规矩；“本对话都允许”不包括它 |
| 用户不知道自己在开一个什么口子 | 开关在库的设置页最下面“高级”里：“允许手写代码”。打开时弹一次说明：“手写代码不经过检查，可能在有的语言里跑不了，也可能做出积木做不到的事。只放你看得懂、信得过的代码。” |

应用可以对函数体做一遍**关键词提示**（出现了起子进程、删文件、`eval`、发网络请求这类写法时，在“先看代码”页把那几行标出来）。**这只是提示，不是安全检查**——换个写法就能绕过去，界面上不许把它说成“已检查安全”。

**“原生片段”**：第 4 版 5.5 说的“一小段手写代码、参数用 `{名字}` 引用”的积木，这里归并成：**项目自己的隐含库（`local`）里的一个原生绑定**。用户看到的流程是“积木盒 › 我的积木 › 新建 › 手写代码积木”：起名字、加参数、选语言、写函数体。它和库里的原生绑定是同一个东西、同一个存法、同一个“手写”标记；只写了一种语言的，在别的语言下是灰的。好处是只有一套机制、一套提示、一套 Agent 确认。骨架第 2 条的“③ 原生片段兜底”就落在这里。

### 8.7 接真正的框架

第 4 版 7.3 说 Express / FastAPI / Spring Boot 作为“带原生绑定的库”接入。按这一节的机制推一遍：

- Express：`新的应用`、`登记路由`、`开始服务` 三个原生绑定加一个第三方包，写得出来。回调是“积木函数”，原生一侧要用小库的“调用”去调——写得出来。
- FastAPI：登记路由靠**装饰器**，而且处理函数是**异步**的、参数靠**类型标注**注入。原生绑定的函数体里可以用 `app.add_api_route(路径, 函数)` 这种不用装饰器的写法登记（**未核对**：这个函数的名字和参数我没有对 FastAPI 官方文档核对）；异步那一头要等“异步”部分定。
- Spring Boot：靠**注解加在类和方法上**，由框架在启动时扫描。包装函数这种形状表达不了“给一个生成出来的类加注解”。**这一种接不了**，记成 GAP-C-12；它本来也受 8.5“Java 不装第三方包”的限制。

## 9. 最小原生接口清单

判定标准只有一条（第 2 节）：**它碰不碰外面的世界**。碰的才进 L0；每一个都要回答“为什么没法用积木搭”。下面的名字是给实现的人看的英文名，用户看到的是标准库或库里的中文积木。

### 9.1 后端宿主：第一批 8 个（做“接口服务”库必须有）

| # | 接口 | 参数 → 返回 | 语义细则 | 为什么没法用积木搭 |
| --- | --- | --- | --- | --- |
| 1 | `sys.print(文字, 通道)` | 文字；通道是 `out` 或 `err` → 空 | 写一行，自动加换行；UTF-8；写完立刻刷出去（否则“运行”页的日志会迟到）。只收文字——别的值怎么变成文字是标准库的事 | 输出是进程和外面之间的口子，语言核心里没有 |
| 2 | `sys.env(名字)` | 文字 → 文字或空 | 没有这个环境变量返回空，不报错；不提供“列出全部”（免得一不小心把密钥全打出来） | 环境变量是操作系统给进程的 |
| 3 | `time.now()` | → 数字 | 从 1970-01-01 零点（UTC）算起的毫秒数，整数。年月日怎么拆、怎么排成文字是标准库的纯计算 | 时钟在外面 |
| 4 | `time.sleep(毫秒)` | 数字 → 空；**要等** | 负数和 0 当 0；只停当前这一件事，不许卡住别的请求（Node 里是等一个定时器，多线程的语言里是停当前线程）。PHP 里一个请求一个进程，停的就是这个请求 | 停下来等时间过去，要靠宿主的调度 |
| 5 | `random.bytes(个数)` | 整数 1–1024 → 数字列表（每个 0–255） | 来自系统的安全随机源。编号、令牌、“随机整数”“随机挑一个”“打乱”都在标准库里用它算，这样五种语言的算法是同一份。现有小库的 `随机整数(a, b)` 保留不动（旧文档在用） | 随机源在外面 |
| 6 | `net.fetch(方式, 网址, 请求头, 内容, 超时毫秒)` | → 字典 `{status, headers, body}`；**要等**；**会出错** | 只许 `http://` `https://`；`headers` 里的名字一律小写；`body` 按 UTF-8 当文字；超时、连不上、网址不对＝抛错，消息五种语言一样；**`status` 是 404、500 不算出错**（是不是算失败由库决定——现在“请求别的网址”积木的“失败后”规矩搬到库里）；跟不跟跳转、响应最大多少沿用第 3 版小库现在的做法，写进宿主的说明 | 网络 |
| 7 | `http.serve(端口, 主机, 处理函数)` | → 不返回（一直服务）；**会出错**（端口被占） | 每来一个请求调一次 `处理函数(请求)`，拿它返回的响应写回去。`请求`＝字典 `{method（方式，大写）, path（路径，原样，没解码）, query（问号后面的原样文字）, headers（请求头，名字小写；重名的用逗号连起来）, body（内容，文字或空）}`。`响应`＝字典 `{status, headers, body}`。（键名用英文，和示例库一致；用户看到的是库里“请求的方式”这类中文积木。）**留在宿主里的规矩**：请求内容超过 1MB 直接回 413，不进处理函数；处理函数抛了错宿主回 500（库自己应该先接住）；响应里的 `status` 不是 100–599 的整数当 500。**搬到库里的规矩**（现在藏在小库里）：跨域头、`OPTIONS` 预检回 204、404 / 405 的内容、端口先看环境变量 `PORT`、主机看 `HOST` | 监听端口、读写网络连接 |
| 8 | `store.read(名字)` ＋ `store.update(名字, 函数)` | 读：→ 任意值（没有就是空）。改：把旧值交给函数、把函数返回的新值存回去、返回新值；**整个过程别人插不进来** | 一个“在请求之间留得住”的格子。Node / Python / Go / Java 是内存里的表加一把锁；PHP 是带锁的文件（它一个请求一个进程）。函数里再调 `store.update` 同一个名字＝报错（否则会自己等自己）。值在存进去和读出来时都是**复制**的（否则 PHP 和别的语言行为不一样：PHP 读出来的一定是副本） | 见下 |

**为什么第 8 个不是第 4 版写的 `store.get / store.set`**：Go 和 Java 的服务是多线程的，两个请求可以同时进来（现有小库里集合的每个操作都包在一把锁里：Go 的 `dbLock sync.Mutex`、Java 的 `synchronized (DB_LOCK)`）。集合的“加一条”如果用积木写成“读出来 → 往列表里加 → 写回去”，两个请求同时加，会有一条丢掉、或者两条拿到同一个编号。锁没法用积木搭（它是宿主的并发机制），所以“原子地改”必须是原生接口。

**为什么格子不直接用“模块级变量”**：Node、Python、Go、Java 里其实可以（进程一直活着）。但 PHP 每个请求是新进程，模块级变量每次都从头来。格子就是为了让五种语言“留得住”的行为一样。库作者要记住的规矩只有一句：**请求之间要留住的东西放格子，不放模块级变量**——校验可以给个警告（模块级变量在帽子的回调里被改、而且目标语言里有 PHP）。

### 9.2 后端宿主：第二批 5 个（文件）

| 接口 | 参数 → 返回 | 语义细则 |
| --- | --- | --- |
| `file.read(路径)` | → 文字；会出错 | UTF-8；文件不在＝抛错 |
| `file.write(路径, 文字)` | → 空；会出错 | 整个覆盖；先写临时文件再改名（断电不留半截）；上层文件夹不在就建 |
| `file.exists(路径)` | → 是否 | |
| `file.list(路径)` | → 文字列表；会出错 | 只列这一层；按名字排好序（五种语言顺序一样） |
| `file.remove(路径)` | → 空；会出错 | 只删文件，不删文件夹 |

- 路径一律相对**工程文件夹**，不许 `..` 跳出去，不许绝对路径——违反＝抛错。
- 为什么要：“返回一个网页文件”“静态文件”“把数据存成文件，重启还在”都要它。为什么排第二批：现有的后端积木一块都用不到它，迁移不依赖它。
- 为什么没法用积木搭：磁盘在外面。
- 只读写文字。读写图片这类不是文字的文件，要先有“字节串”类型（GAP-C-9）。

### 9.3 审过、决定不放进 L0 的

| 能力 | 放哪 | 理由 |
| --- | --- | --- |
| JSON 互转 | 标准库（L2） | 纯计算。五种语言自带的 JSON 在数字写法、键的顺序、转义上各不相同，所以现有小库本来就是自己手写的一份（`LcJson.java`、`lc_json.php`）——继续做标准库的一部分 |
| 网址的百分号编码 / 解码 | 标准库 | 纯计算 |
| Base64、十六进制 | 标准库 | 纯计算 |
| 加密哈希（SHA-256 等）、HMAC | 标准库（它的实现是原生的） | 纯计算，但用积木算会慢到不能用，所以标准库里用各语言自带的实现——它是“因为慢才用原生”，不是“因为碰外面”。**五种语言自带的哈希函数叫什么、要不要额外的包，未核对** |
| 密码哈希（bcrypt 之类） | 带第三方包的库 | 各语言标准库里**不齐**（未核对具体哪些有），不该进标准库 |
| 定时任务（每隔多久做一次） | 库 | “开始做 { 一直重复 { 睡眠；做事 } }”就搭出来了。PHP 没有常驻进程 → 这块在 PHP 下是灰的 |
| 静态文件 | 库 | 路由 ＋ `file.read` ＋ 按扩展名查内容类型（一张表，纯数据） |
| 进程参数 | 不做 | 生成的程序没有人给它传参数；要配置用环境变量 |
| 起子进程、跑命令 | **不做** | 太危险，而且 Agent 已经有终端 |
| WebSocket、流式响应（一点一点往回写） | 现在的模型表达不了 | `http.serve` 的约定是“处理函数返回一个完整的响应”。长连接要另一种接口（“来了一个连接，给你一个能反复写的东西”）。这一轮不做，记 GAP-C-13 |
| 数据库（SQLite、MySQL…） | 带第三方包的原生库 | 不是每个项目都要；各语言标准库里也不齐 |

**还能不能更少**：`time.sleep` 可以用“一直看时钟”代替——但那是空转烧电，不行。`sys.env` 可以去掉、让端口只走设置项——但部署到服务器上时改端口的惯例就是环境变量，现有小库已经在读 `PORT`，去掉会改变现有行为。结论：8 个里没有能再去掉的。

**够不够**：对“改写现有后端积木”够（第 14 节逐块推过）。对“返回网页”要第二批。对“上传文件、返回图片”不够（GAP-C-9）。

### 9.4 浏览器宿主

**决定（给 D 的建议）：最小集合不是“一堆 DOM 接口”，而是一组通用的“碰 JS 对象”接口。**

浏览器里的所有能力——DOM、事件、定时器、`fetch`、本地存储、地址栏、历史、控制台、剪贴板、画布——在 JS 里都是“某个对象的属性和方法”。所以只要有下面 7 个，其余的都能在库里用积木封装出来：

| # | 接口 | 意思 | 为什么没法用积木搭 |
| --- | --- | --- | --- |
| 1 | `js.global(名字)` | 拿一个全局的东西：`document`、`window`、`localStorage`、`location`、`history`、`console`… | 这些对象是浏览器给的 |
| 2 | `js.get(对象, 属性名)` | 读属性 | 积木的“字典取键”管的是我们自己的字典，管不了浏览器的对象 |
| 3 | `js.set(对象, 属性名, 值)` | 写属性 | 同上 |
| 4 | `js.call(对象, 方法名, 参数列表)` | 调方法 | 同上 |
| 5 | `js.new(构造函数, 参数列表)` | 新建一个浏览器的对象（`new URL(…)`） | 同上 |
| 6 | `js.callback(积木函数)` | 把积木里的函数变成浏览器能调的函数（事件监听、定时器的回调要它） | 两边“函数”不是同一种东西 |
| 7 | `js.await(可等待的东西)`；**要等** | 等一个浏览器给的“以后才有结果的东西” | 同上 |

再加 5 个**和后端同名**的通用接口，为了让 `hosts: ["any"]` 的库两边都能用：`sys.print`（到控制台）、`time.now`、`time.sleep`、`random.bytes`、`net.fetch`（约定和后端一样；浏览器里多一条“会被跨域规矩拦住”）。它们在浏览器里的实现其实就是用上面 7 个写的，单列出来只是为了同名。

逐个审任务里点到的：

| 能力 | 用什么封装 | 要不要单独的原生接口 |
| --- | --- | --- |
| DOM 增、删、改、查 | `js.call(document, "createElement" / "querySelector" …)`、`js.set(元素, …)` | 不要 |
| 事件 | `js.call(元素, "addEventListener", [名字, js.callback(函数)])` | 不要 |
| 定时器 | `js.call(window, "setTimeout" / "setInterval" …)` | 不要 |
| `fetch` | 已有同名的 `net.fetch` | 已列 |
| 本地存储 | `js.global("localStorage")` ＋ `js.call` | 不要 |
| 地址栏与历史 | `js.global("location" / "history")` | 不要 |
| 控制台 | `sys.print` | 已列 |
| 弹提示 | `js.call(window, "alert", …)` | 不要 |

**一个必须留着的例外：改页面编辑器里画出来的控件**。第 4 版 6.1 的页面接口（`dom.find` / `dom.get` / `dom.set` / `dom.on` / `page.onLoad`）不能全换成上面的通用接口，因为导出成 Vue、React 时，**控件的内容归框架管**：直接改 DOM，框架下一次重画就给盖掉了。现在 `JsTarget` 的三个子类干的正是这件事（普通网页直接改 DOM，Vue 改 `ref`，React 改状态）。所以“页面”库最底下要留一小组**控件级**的原生接口（读 / 写某个控件的某个属性、给某个控件挂事件、页面打开时），由宿主按导出的框架各给一份实现。

**这一小组具体几个、怎么和 Vue / React 的状态对上，由 D 细化。** 浏览器这一节里涉及的 JS 名字（`addEventListener`、`querySelector`、`localStorage` 等）我是凭常识写的，**没有逐个对 MDN 核对**，D 那边核对。

通用接口的代价要说清楚：`js.call(对象, "方法名", …)` 的方法名是文字，写错了要到运行时才知道；类型也说不出来。所以它**只给库的作者用**（积木盒里默认不出现，放在“高级”里），普通用户用的是库封装好的、带类型的积木。

## 10. 用户怎么新建、编辑、分享、导入库

### 10.1 库放在哪

| 位置 | 是什么 | 谁能改 | 跟着什么走 |
| --- | --- | --- | --- |
| **内置** | 应用自带的（“接口服务”“页面”“小路由”示例…） | 只读 | 跟应用版本 |
| **我的库** | 应用文档目录下 `libs/作者段/库名/`，这台手机上所有项目都能“用上” | 能改 | 跟这台手机（卸载应用就没了——界面上要说，并给“全部导出”） |
| **项目里** | 项目的 `blocks/作者段/库名/` | 能改 | 跟项目（进 git、进导出的压缩包） |

“用上”＝从“我的库”或内置**复制一份进项目**（内置的不复制，5.4）。在项目里改库只改项目里的这一份；改完想让别的项目也用，点“存回我的库”（版本号要比“我的库”里的大，否则提醒）。

项目里“我的积木”（`local` 隐含库，12.3）不用新建，天生就有。

### 10.2 入口

侧边栏 › **积木库**（新的一页，一级入口；也可以从积木盒最下面一行“管理库…”进来）。页面从上到下，一行一件事：

```
积木库
────────────────────────
这个项目用上的（2）
  [图标] 接口服务            内置 · 1.0.0        ›
  [图标] 小路由              demo · 1.2.0  有新版 ›
我的库（3）
  [图标] 表单校验            1.1.0               ›
  …
内置（6）
  …
────────────────────────
[ 新建库 ]
[ 从文件导入 ]
```

### 10.3 新建和编辑

**新建**（三步，每步一屏）：

1. 名字（可以中文）→ 自动给出标识的后一段（拼音或让她自己打英文；不合规矩当场说哪里不合），作者段用“我的署名”（第一次要填）。
2. 给谁用：后端 / 页面 / 都行（就是 `hosts`）。
3. 放哪：我的库 / 只放这个项目。→ 建好，直接进第一个模块的画布。

**编辑**用的是**同一张积木画布**，只多三样：

- 顶栏标题是“库名 › 模块名”，点它切换模块、新建模块。
- 积木盒里多一组“这个库的”（库自己的定义，含不公开的）。
- 每个定义的帽子（定义帽、类卡片）按住的菜单里多一行“公开 / 库内 / 只给这个模块”；公开的定义帽右上角有一个小的“公”字标。

库的主页（点库的卡片进来）一行一件事：说明、版本（点了改）、模块（列表）、积木（列表，点进去是现有的“新建积木”页，多了“背后是哪个定义”“预填参数”）、规则、清单、设置项、用例（[跑一遍]）、示例、依赖、高级（允许手写代码、支持的语言、导出、删除）。

**“包成库”的捷径**：项目里已经有几块“我的积木”了，多选 → “移到库里…” → 选一个库或新建。文档里的调用自动从 `call:f1` 改成 `库标识#编号`，可以撤销。

### 10.4 导出和导入

**导出**：库主页 › 导出 → 先跑校验和用例（有错误不让导出；有警告、有没跑过的用例照样能导出但写明）→ 检查版本号够不够（5.5）→ 生成一个 `小路由-1.2.0.lopilib` → 系统的分享面板。

`.lopilib` 就是库文件夹打的 zip 压缩包（工程里已经有 `archive` 这个依赖，不用加新的）。文件名只是给人看的，标识和版本以里面的清单为准。

**导入**：积木库 › 从文件导入 → 选文件 → **预览页**（这时什么都还没写进手机）：

```
小路由                      demo/mini-router · 1.2.0
作者：demo        许可证：MIT
一个最小的路由库……
────────────────────────
里面有
  积木 5 块 · 函数 4 个 · 规则 5 条 · 用例 6 条
依赖
  （没有）
────────────────────────
要注意的
  ⚠ 含手写代码 3 段（Node、Python、Java）      [ 看代码 ]
     手写代码没有经过检查。运行时它能做
     这个项目的运行环境里能做的任何事。
  · 不用装第三方包
  · 要用到：开 HTTP 服务、读环境变量
────────────────────────
[ 取消 ]      [ 导入，先不允许手写代码 ]
              [ 导入并允许手写代码 ]
```

- **“要注意的”一节只在有东西时出现**：手写代码（段数、哪几种语言）、要装的第三方包（逐个列名字和版本）、要用到的宿主接口（用人话：“发网络请求”“读写项目里的文件”“读环境变量”）。
- **带手写代码的库**：“导入并允许手写代码”这个按钮要**先点开过“看代码”才亮**。选“先不允许”的话，库照样导入，只是用到手写代码的积木是灰的，以后可以在库的“高级”里再打开（再打开时同样要先看代码）。库更新后手写代码变了，开关自动关上，要重新看。
- **标识撞了**（“我的库”里已经有同一个标识）：版本更高 → 问“替换成新版（列出变化，5.5）/ 取消”；版本一样但内容不同、或版本更低 → 问“替换 / 另存成新的标识（让她改库名那一段）/ 取消”。
- **坏文件**：清单读不了或标识不合规矩＝“这个文件不是一个能用的库”，写出具体哪里不对；别的坏处照 3.1 的三档处理，预览页上写“有 2 块积木读不了，已跳过”。

**导入时的防护**（都是读文件这一步做的，不靠用户小心）：

- **导入不执行任何东西**：不跑用例、不生成代码、不装包。要跑要装，都是以后用户自己点。
- 压缩包里的路径逐个过现有的 `PathGuard`：带 `..`、绝对路径、符号链接的条目直接丢掉并记一笔。
- 上限：解开以后总共不超过 8MB、不超过 512 个文件、单个文件不超过 1MB（清单 256KB）——超了不导入，说明是哪一条超了。这几个数是我定的初值，没有依据别的系统，可以调。
- 只认清单点到的文件和固定位置的文件（3.2 的结构）；压缩包里别的东西不解出来。
- 作者段是 `lopi` 或 `local` 的拒绝；`legacyOps`（旧名对照）即使写了也不生效（3.3 已说：否则一个导入的库能冒名顶替旧积木）。

**不做的**：在线商店（要账号、审核、举报、服务器，每一样都是长期的事；而且带手写代码的库放上商店，审核责任在我们）。**“从网址导入”建议这一轮也不做**——它等于“联网下载一段别人写的代码”，照工程规矩要先问、要显示来源、要校验；先看“发文件”这条路用得怎么样。（要霜霜拍板，见文末。）

### 10.5 内置库只读；“复制一份来改”

- 内置库能“看里面”：所有模块、定义、积木都能打开看，不能改（画布是只读的，顶栏写“内置 · 只读”）。这就是霜霜要的“能点进‘返回数据’看它是怎么搭的”。
- **“复制一份来改”**：整个库复制到“我的库”或项目里，**必须换标识**（默认 `我的署名/原库名`），清单里记 `origin: {id, version}`（从哪个库的哪一版复制来的）。
- 复制以后和原库的关系：**断开**。原库更新不会动这一份；这一份的主页上有一行“从『接口服务 1.0.0』复制来的；原库现在是 1.2.0”——只告知，不提供自动合并（合并两份积木定义，手机上讲不清）。
- 复制完问一次：“把这个项目里用『接口服务』的地方，都换成用你这一份吗？”——换＝文档里的 `lopi/http-service#…` 改成新标识（积木编号没变，所以一一对得上），可以撤销；不换＝两个库并存，积木盒里两个分类。
- 注意：旧文档里的旧 op 名（`respondJson`）**永远指向内置库**。换成自己那一份以后，这些积木会被改写成带库标识的新写法——这是“不改就不重写”的一个例外，所以要先问。

### 10.6 Agent 读写库的工具

照现有 `backend_update_blocks` 的路子（先校验、有错误不落盘、原子写、返回问题清单）：

| 工具 | 干什么 | 要不要确认 |
| --- | --- | --- |
| `lib_list` | 列出内置 / 我的库 / 项目里的库：标识、版本、公开积木的清单（名字、槽、说明） | 不要 |
| `lib_read` | 读一个库的清单、某个模块、规则、用例。内置库也能读（Agent 学怎么写库最好的办法就是读内置库） | 不要 |
| `lib_write` | 新建库 / 改清单 / 整个替换一个模块 / 改规则 / 改用例。只能写项目里的库和“我的库”；**不能写内置库** | 和现在写文件一样 |
| `lib_write_native` | 写或改一段手写代码 | **每次都要**，确认卡上显示完整代码；“本对话都允许”不包括它 |
| `lib_use` | 让某份文档“用上”/ 不再用某个库 | 要装第三方包时走装包的确认 |
| `lib_test` | 跑库的用例，返回每条过没过、差在哪 | 不要（快跑不联网；“在所有语言里跑”要环境已经装好） |

Agent **不能**替用户点“允许手写代码”的开关，也不能导入外面的 `.lopilib`（那是用户的决定）。

## 11. 库的测试

### 11.1 用例怎么写

库的 `tests/*.json` 里两种东西（完整的例子见 3.4 的 `tests/router.test.json`）：

**用例**（`cases`）——“给这些输入，应该得到这个输出”：

```json
{"name": "带参数的路径对得上", "call": "match", "args": ["/todos/:id", "/todos/42"], "expect": {"value": {"id": "42"}}}
{"name": "空路径报错", "call": "match", "args": ["", "/"], "expect": {"error": "路径不能是空的"}}
{"name": "编号是 36 个字", "call": "newId", "args": [], "expect": {"check": {"type": "文字", "size": 36}}, "targets": ["node", "python", "java"]}
```

- `expect.value`：结果转成规范的 JSON 文字以后**逐字节**相等。
- `expect.error`：应该抛错，消息相等。
- `expect.check`：结果说不准（随机、时间）时只检查类型、长度（`size`）、正则、范围。
- `targets`：这条只在这几种语言里跑（用到的手写代码只有这几种语言时要写）。
- `call` 可以是不公开的定义（库自己测自己）。

**场景**（`scenes`）——库要碰宿主时，给一个**假宿主**：

```json
{"name": "打招呼", "program": "examples/hello.json",
 "host": {"fake": ["http.serve", "time.now", "random.bytes", "sys.env", "net.fetch"],
          "values": {"time.now": 1700000000000, "random.bytes": [1, 2, 3, 4], "sys.env": {"PORT": "9000"},
                     "net.fetch": [{"when": {"url": "https://x.test/a"}, "reply": {"status": 200, "headers": {}, "body": "ok"}}]}},
 "steps": [
   {"request": {"method": "GET", "path": "/hello/小明", "query": "", "headers": {}, "body": null},
    "expect": {"status": 200, "body": "{\"message\":\"你好，小明\"}"}, "printed": []}
 ]}
```

（3.4 的示例只用到了 `fake: ["http.serve"]` 和 `steps`；`values` 和 `printed` 是这里补充的两个可选字段。）

假宿主的意思：`http.serve` 不真的开端口，而是把 `steps` 里的请求一个个喂给处理函数、拿响应和 `expect` 比；时钟、随机、环境变量、对外的请求都是写死的。**因为 L0 只有那十几个接口，假宿主才做得起来**——这是第 2 节把 L0 压到最小的直接好处。

在手机上写用例：库主页 › 用例 › 新建 → 选一块积木或一个定义 → 每个参数一行填值 → “先跑一次，把结果记成期望值”（多数用例是这么来的）→ 存。

### 11.2 在手机上怎么跑

| 跑法 | 要什么 | 能说明什么 |
| --- | --- | --- |
| **快跑** | 什么都不用装 | 库的逻辑对不对。把库和用例生成成 JavaScript，放进应用自带的网页内核里跑（工程已经依赖 `webview_flutter`，页面预览在用），宿主接口全用假的。**手写代码跑不了**（除非它写的是浏览器 JS）——结果里写“3 条用到手写代码，没跑” |
| **在所有语言里跑** | 运行环境和对应的语言已经装好 | 五种语言是不是一样。每种装了的语言生成一个小工程（库 ＋ 用例 ＋ 假宿主的那种语言版本），跑完把每条用例的输出**逐字节**比。没装的语言写“没装，没跑”，**不许算成通过** |

结果页一行一条：名字、过 / 没过；没过的点开看“期望 / 实际”（两段文字用现成的对比视图）和是哪种语言。

**快跑没验证过**：在网页内核里跑生成的 JS、把结果传回 Flutter，这条路现在没有人走过（页面预览只是显示网页，没有往回要结果）；`webview_flutter` 能不能执行脚本并取回结果、有没有大小限制，**未核对**，实现前要对官方文档核对。它还意味着应用里要有一个“后端库 → 浏览器 JS”的生成路子——后端的 Node 目标和页面的 JS 目标现在是两套生成器，共用到什么程度要看语言核心那部分的结论。

### 11.3 内置库怎么保证五种语言一致

1. **每块公开积木至少一条用例**，否则合不进来（写成一条 Dart 测试去数）。
2. **沿用现有的一致性测试**（`test/lang_conformance_*_test.dart` 和 `test/backend_conformance_test.dart` 那一套：同一份程序在几种语言里真跑、逐字节比）。内置库的用例和场景全部进这套测试。现状要如实写：这套测试在开发机上真跑的是 Node、Python、Go、Java；**PHP 本机没有，一直没真跑过**。
3. **迁移的守门**（12.2）：现有后端测试里的每一份文档，用“库版”重新生成，和旧小库版**对同样的请求给出同样的响应**（状态码、响应头、内容逐字节）。不一样就是库写错了。
4. 假宿主本身五种语言各一份，也要测：同一个场景文件，五种假宿主给出的记录要一样。

用户库没有第 2、3 条的保证。库的卡片上如实显示：“用例 6 条 · 快跑全过 · Node、Python 跑过 · Go、Java、PHP 没跑”。

## 12. 和现有东西的迁移

### 12.1 旧文档照常打开

原则不变（第 4 版 8.1）：**原样能开，不改就不重写文件。**

| 旧文档里的 | 怎么认 |
| --- | --- |
| 不带库标识的 op（`respondJson`、`dbInsert`、`setProp`…） | 查内置库的 `legacyOps`（旧名 → 积木编号）。后端文档查“接口服务”，页面文档查“页面” |
| 没有 `uses` | 内置库清单里的 `autoUse`：`backend.lc.json` 自动算作用上了“接口服务”；页面的逻辑文档自动算作用上了“页面” |
| 顶层的 `collections` | “接口服务”库 `collections` 清单的 `legacyKey`（7.5） |
| 顶层的 `port`、`language` | `port` ＝“接口服务”的设置项（7.6）；`language` 是文档自己的，不归库 |
| `functions[]`、`call:f1` | 不动（12.3） |
| 旧槽名 | 积木定义里每个槽可以带 `legacyName`。“接口服务”库的槽名直接沿用旧名，基本用不上 |

存的时候：文档里没有用到任何新东西，就按旧格式原样写回去（版本号不升）。用到了（比如用上了第二个库），才写新字段、升版本号——旧版应用打开它会说“这份文档是新版应用存的”（现有的做法）。

### 12.2 改写内置库：怎么保证行为不变

1. 先加后换：库版和旧小库版**并存**一段时间，由一个开关决定生成哪一种；守门测试（11.3 第 3 条）全过以后才把默认值换过去；再过一个版本才删旧小库里搬走的那部分。
2. 旧小库约 2200 行里（1.2）：搬进库的是纯逻辑（路由匹配、404 / 405、网址参数、状态码兜底、集合增删改查、自动编号、跨域头、`OPTIONS`）；留下的是 L0 的实现（开端口、读写请求、1MB 上限、文件锁、对外请求）。**粗估**留下的每种语言 150–250 行——这是我看着小节行数估的，没有真的拆过。
3. 会变的地方要提前说：
   - **生成的代码变长了、变了样**：路由匹配从小库里的手写代码变成库生成的代码。“看代码”里入口文件不变，多出 `lib/http_service/` 一个文件夹。
   - **日志里的文字可能变**：现在处理函数出错时小库会打印那种语言自己的出错堆栈；改成库以后，库里“试着做”接住的只有消息。响应不变，日志变了。
   - **速度**：积木写的路由匹配比手写的慢。**慢多少没量过**；路由表不大时应该看不出来，但这是猜的，守门测试里要加一条量时间的。
4. 34 条规则归到哪：

| 规则 | 归到 | 怎么声明 |
| --- | --- | --- |
| G01–G13、S10、S11、S12 | 核心（第 4 版 8.3，不变） | — |
| G14 网址不像网址 | 标准库“发网络请求”积木的槽约束 | `slot` |
| S01 端口 | “接口服务”设置项的范围（设置项自带检查，不占规则） | 设置项的 `min` `max` |
| S02 选的语言不能生成 | L06（8.4 算出来的） | — |
| S03 / S04 集合名、集合不存在 | 清单的 `namePattern` ＋ `picker` 槽“必须是清单里有的” | 清单 ＋ `slot` |
| S05 方式、S06 路径格式、S13 状态码 | 槽约束 | `slot` |
| S07 接口重复 | 唯一约束（路径比之前把 `:名字` 都换成 `:`） | `unique` ＋ `normalize` |
| S08 被前面的挡住 | 有名字的检查器 `routeShadow` | `checker` |
| S09 取了路径里没有的参数 | “从帽子的路径槽里提取”的清单 ＋ `picker` 槽 | 清单（`source: slot`） |
| P01 控件已经不在页面里 | 清单（宿主给的“页面上的控件”）＋ `picker` 槽“必须是清单里有的” | 清单（`source: host`） |
| P02 事件没选控件 | 槽约束（必填） | `slot` |
| P03 “内容变化”挂在不是输入框的控件上、P06 控件没有这个属性 | 槽间约束（能选什么取决于选了哪种控件） | `relate` |
| P04 不认识的事件 | 核心的“不认识的积木”（旧文档里的事件名在“页面”库的旧名对照表里查不到） | — |
| P05 “输入的内容”用错了地方 | 位置约束；做成帽子的参数小块以后自然成立 | `place` |
| P07 同一个控件的同一个事件有两串 | 唯一约束 | `unique` |

（规则的原文对过 `lib/lowcode/logic_rules.dart` 的规则表。）编号一个都不改。

### 12.3 “我的积木”和库的关系

**决定：“我的积木”＝项目自己的一个隐含的库，标识 `local/项目`，不用新建、不能删、不能导出。**

- 现在存在每份文档里的 `functions[]`（`{id, look, params, body, x, y}`）**原样不动**：它被当成“隐含库里、只给这一份文档用的一个模块”。`call:f1` 照旧。老文档一个字不用改。
- 新增一个地方：项目的 `blocks/local/` ——“项目积木”，整个项目里所有文档（后端的、每个页面的）都能用。它解决现在的一个实际不便：一块“我的积木”只能在定义它的那一份文档里用。
- 积木盒里“我的积木”一个分类，分两组：“这份文档的”“项目的”。按住一块 →“移到项目里”（调用从 `call:f1` 改成 `local/项目#编号`；这块里不能用到宿主专属的东西，除非项目里所有文档都是同一种宿主——校验拦）。
- 从“项目的”再往外一步就是 10.3 的“移到库里…”。**三级：这份文档 → 这个项目 → 一个能发给别人的库**，每一级都是同一种格式、同一张画布，只是“谁能用”越来越宽。
- 手写代码积木（8.6 的“原生片段”）也放在这个隐含库里。

B01–B09（第 2 阶段的 9 条“我的积木”规则）继续管外观本身，对库里的积木同样生效。

## 13. 别人是怎么做的

只学思路。每家后面写了我核对的是哪一页；核对不了的标了“未核对”。

| | 它的库 / 扩展是什么 | 值得学的 | 不适合我们（手机、五种语言）的 |
| --- | --- | --- | --- |
| **Scratch 3 扩展** | 一个 JavaScript 类。`getInfo()` 返回扩展的 `id`、`name`、一组 `blocks`（每块有 `opcode`、`blockType`、`text`——文案里方括号是参数、`arguments` 里写每个参数的类型和默认值）和 `menus`（下拉清单）；每个 `opcode` 对应类里一个同名的方法。官方文档写明 Scratch 3.0 当时还不支持非官方扩展，并且强调向后兼容：积木的定义和 `opcode` 不能改到让旧项目打不开 | ①“扩展编号 ＋ 积木编号”认积木，文案只是显示——我们的 `库标识#积木编号` 是同一个思路。②文案模板里用方括号标参数。③`menus` 就是“清单类的槽”。④“编号永远不许改”的兼容纪律 | 扩展就是一段 JS，积木的行为全是手写代码——那等于“每块积木都是原生绑定”，和“用基础积木封装”正相反；也只有一种目标语言 |

### 14.1 第 4 版 6.2：后端积木逐块过

### 14.3 第 4 版 7.1：小路由的例子

逐行推下来，例子**照它写的那样跑不通**，有四处：

1. **`app` 在“启动时”里新建，下面的帽子却要用它。** “启动时”里新建的变量是那一串自己的，帽子看不见；就算看得见，帽子的登记如果先于“启动时”跑（7.7 的顺序），那时 `app` 还不存在。要么 `app` 是模块级变量（先于一切初始化），要么“当 {应用} 收到…”这种带对象的帽子不成立。→ **GAP-C-14**（模块级变量）＋ **GAP-C-2**（顺序）。
2. **“让 (app) 在端口 8080 开始服务”写在“启动时”里。** 按 7.7 的顺序它在帽子登记之后跑，这一条是通的；但 `http.serve` 不返回，它后面不能再有积木——这块应该是收尾型，例子里是语句型。
3. **外观绑在方法和构造上**（“当 {应用} 收到 GET {路径}”＝方法 `加路由` 预填 `"GET"`；“(新的应用)”＝构造）。第 2 阶段的外观只能绑在文档里的函数上。→ **GAP-C-1**。
4. **中间件“返回了响应就不往下走”**：例子靠“返回空＝继续”。能表达，没有缺口；但“空”既是“继续”又可能是“忘了返回”，库的文档里要写清。

例子里的类本身（字段、方法、`这个对象`）依赖第 5 阶段，不算库体系的缺口。**不用类也能写出同样的库**（3.4 的示例库就是：一个模块级的路由表加几个函数），只是做不出“两个互不相干的应用”。

### 14.4 第 4 版 7.2：计数器组件的例子

1. **`计数器` 在“当页面打开”里新建，“当按钮被点击”里要用。** 同 14.3 第 1 条 → **GAP-C-14**。
2. **“(新的组件 根 {控件} 状态 {字典} 怎么画 ＋回调口)”是一块带口的值积木。** 值积木是放在别的积木的槽里的，口里又要竖着放一串语句——390 宽的屏上，一块嵌在槽里的积木下面再挂一个口，画不下也拖不准。第 2 阶段的规则里口只出现在语句型和帽子型上。→ **GAP-C-15**：要么不许值型带口（这个例子改成语句型：“新建组件 放进变量 [x] … ＋口”，那又要写入目标槽，GAP-C-3），要么编辑器专门设计这种形状。**建议前一种。**
3. **“怎么画”的回调里直接改控件**，在普通网页下可以；导出成 Vue / React 时就是 9.4 说的问题——归 D。
4. “状态一变就重画”能用积木表达，没有缺口。

### 14.5 第 4 版 7.3：真框架

见 8.7：Express 写得出来；FastAPI 要等异步的结论（GAP-C-5）；Spring Boot 靠注解，包装函数的形状表达不了 → **GAP-C-12**。

### 14.6 推演之外想到的

- 原生绑定的作者拿到“列表 / 字典 / 任意”类型的参数时，需要小库给的互转函数，现在没有对外给 → **GAP-C-11**。
- 长连接、一点一点往回写的响应，“处理函数返回一个响应”的模型表达不了 → **GAP-C-13**。

### 14.7 结论

**只靠“函数 ＋ 类 ＋ 外观 ＋ 原生绑定”不够。** 还要补的东西分三堆：

- **外观这一层要加的**（这份文档已经给了设计，第 7 节）：一个定义多个外观和预填参数（1）、展开型积木和写入目标槽（3）、隐含的上下文参数（4）。
- **库这一层要加的**（已经给了设计）：设置项（6）、“最后启动”（7）、顶层的执行顺序（2）、格子的原子修改（8）。
- **要别的部分给结论的**（这里只提出问题）：回调要等的时候（5，异步）、字节串（9，类型）、模块级变量和多模块（14，语言核心）、值型带口（15，编辑器）、注解和装饰器（12）、长连接（13）、应用内解释器（10）、互转函数（11，标准库）。

### 和骨架 / 第 4 版不一致的地方

1. **JSON 互转、百分号编码不算宿主接口，归标准库**（第 4 版 6.1 把它们列在“通用宿主”里）。理由：不碰外面的世界；L0 小了假宿主才做得起来。
2. **`store.get / store.set` 换成 `store.read / store.update`**（GAP-C-8）。
3. **“原生片段”不单设机制**，并进原生绑定（8.6）。第 4 版 5.5 写的是“代码模板、参数用 `{名字}` 引用”；这里改成“包装函数、参数就是函数的参数”。
4. **声明式规则从三种变四种**（加“槽间约束”），另加“从别的槽里提取的清单”。
5. **第 4 版 8.3 说“内置库可以带 Dart 写的规则，用户库不行”**，这里改成“应用里有名字的检查器，内置库和用户库都按名字引用，都不能新写”——为了内置库和用户库是同一种格式。
6. **`http.serve` 的约定里多了“主机”参数**；跨域头、`OPTIONS`、端口看环境变量这三样从宿主搬到库里。
7. **第 4 版 7.1 的例子照原样跑不通**（14.3 的四处），要按模块级变量和 7.7 的顺序改写。
8. 第 4 版 6.2 说数据集合做成“类”；这里指出用函数就够，“接口服务”库不必等类实现。
9. **不做“一个库同时有后端和页面两部分”**（7.8），前后端共用的纯计算做成 `hosts: ["any"]` 的库。

### 要霜霜拍板的（3 件）

| # | 问题 | 选项 | 建议 |
| --- | --- | --- | --- |
| 1 | 用户自己写的库，能不能带手写代码（原生绑定）？ | A 能，默认关着，打开时说明，导入时要先看代码，Agent 写要逐次确认；B 不能，只有内置库能带 | **A**。不能带的话，用户的库永远只能在我们给的那十几个接口上打转，接不了任何第三方的东西 |
| 2 | 要不要“从网址导入库”？ | A 这一轮不做，只能发文件；B 做（联网下载，先问、显示来源） | **A**。先看发文件用得怎么样；在线商店同样不做 |
| 3 | Java 下需要第三方包的库，这一轮做不做？ | A 不做（这类库在 Java 下是灰的）；B 做（要在手机上装 Maven 或 Gradle，很重） | **A** |

别的决定我都给了默认，不用她逐条看；她要是对其中哪条有不同想法，最可能是这两条，协调者可以顺带提一句：库的标识用“我的署名/库名”两段英文（4.1）；一个项目里一个库只留一个版本（5.3）。

### 没核对、没跑、看不出来的

**没核对（事实）**

- 五种语言各自“查一个包装没装、装一个包”的命令和依赖文件的确切写法（8.5）。
- Blockly 的插件机制；Snap! 现行版手册；App Inventor 扩展的官方页面（第 13 节）。
- 浏览器接口的名字和行为（9.4）——归 D。
- 五种语言标准库里哈希函数的名字、哪些语言标准库自带 WebSocket / 密码哈希（9.3）。
- FastAPI 不用装饰器登记路由的函数名（8.7）。
- `webview_flutter` 执行脚本并取回结果的接口和限制（11.2）。
- 示例库里积木体的键名（`args`、`pairs`、`of` 等）没有逐个对 `backend_blocks_lang.dart`（3.4 已注明）。
- 现有小库在“请求内容不是合法 JSON”时各语言的处理（14.1）。

**没跑**

- 示例库没有被任何程序读过、校验过、生成过代码——现在没有读库的代码。
- 4.3 的命名方案里，Node、Python、Java、PHP 的文件布局和导入写法都没跑；8.2、8.3 的包装函数生成没跑。
- “快跑”（在网页内核里跑用例）没跑。
- PHP 的一切（本机没有 PHP）。
- 第 14 节是纸面推演。

**跑过的只有三件**（都是几行的小实验，放在 `/tmp/v5-C/`，不是产品代码）：

1. 示例库的五份 JSON 用 Python 的 `json.load` 读过，是合法的 JSON；规则文件里的三条正则在 Python 里试过（结果见 3.4）。
2. “生成编号”三段手写代码各跑过一次：Node v24.22.1、Python 3.12.3、Java 21，都得到 36 个字符、第 15 个是 `4`。
3. Go 1.25 下一个两包的小程序：包名 `mini_router`，调大写开头的 `F_reply` 打出 `201`；改成调小写的 `f_hidden`，编译报 `name f_hidden not exported by package mini_router`。

**看不出来的**

- 第 12.4 节的返工量、12.2 的“每种语言留下 150–250 行”都是估计。
- 积木写的路由匹配比手写的慢多少。
- 导入上限（8MB、512 个文件、1MB）是我定的初值，没有依据。
- 库生成的代码和语言核心“模块”部分怎么对接（各语言的导入、会不会绕圈），要等那部分定了再对。
