1. **三样都写出来、真跑通了，但第 1 轮三样都不过**，每样都逼出了基础层的改动。两轮结果（期望都是第一次运行之前手写的，没有为了通过改过）：

2. **最重的一条：“要不要等”必须进函数类型（GAP-F2-01）。** F1 把它记成一个洞；到前端它是堵墙——第 1 轮“调函数值一律等”，读一个派生值都会在半路让出，攒着的更新插进来，状态库在 Node 里直接算错、崩掉。第 2 轮规定“库的回调是不用等的函数”以后才对。
3. **只靠 D 的 9 个界面语义级接口，组件用积木写不出来（GAP-F2-05）。** 它们不能造元素、放元素、拿元素，D 把“重复”和“存在条件”交给了导出器。第 2 轮加了 4 个元素级宿主接口，用积木写了一个 164 行的“画面库”，组件（属性、事件、插槽、自己的状态、两个生命周期、多个实例、拿走后自动收尾）才完全由封装得来。这和 C 的方向一致、和 D 不一致，要拍板。
4. **F1 的 `net.fetch`（不成功一律得空）撑不起前端（GAP-F2-09）**：显示不了服务器说的校验原因。换成 D 的“网络.请求”（任何状态码都拿得到回应）后通过。建议前后端宿主统一成这一个。
5. 第 2 轮对核心的增补只有三样：`call!`（调不用等的函数）、标准库 `isSame`（是不是同一个）、清单里的“懒值”槽（式子先不算）。宿主接口新增 5 个：元素级 4 个 ＋ `net.request`。
6. 缺口一共 **14 条**（GAP-F2-01…14）：原型里补上的 5 条（01、02、03、05、09），绕过去或自己定了规矩的 4 条（04、08、10、11），只记下没补的 5 条（06、07、12、13、14）。
7. **没跑的**：真浏览器、Vue / React、PHP / Go / Java；04、05 的前端只在 Node 假页面里跑（没有做 Python 假页面）；假页面不是浏览器（没有排版、默认行为、捕获阶段）。
8. 需要霜霜拍板的 3 件（第 8 节）：回调“要不要等”的规矩；普通网页里组件走“元素级接口＋积木写的画面库”还是维持 D 的“导出器生成”；发请求接口前后端统一。

## 2. 第 1 轮结果与发现

第 1 轮的失败输出原样留在各目录的 `round1/RESULT-round1.txt`；每次重跑都会核对“和留档的一样”。

### 2.1 03 前端小库：Node 6/48，Python 45/48

- **Python 不过的 3 条**（[5b][5c][5d]）：数字 1 换成文字“1”、换成内容一样的另一个列表，都应该算“变了”，实际不算。原因：标准库只有“宽松相等 / 深比较”的 `==`，没有“是不是同一个”。
- **Node 只过前 6 条，然后程序以 1 退出**，错误输出一行：`没接住的错误：派生值的算法里不能改状态`。这句话是假的——检查程序那时没有在算派生值。

### 2.2 04 组件：13/25

只用 D 的读、写、当事件，页面上的控件得事先摆好（真产品里是编辑器摆、导出器生成），组件只能“认领”有名字的控件。不过的 12 条：

- [9] 行数是摆死的三行，第四条画不出来。
- [12][13][15] 删一条 / 调顺序：树的文字是对的，但宿主被要求写了 5 次（期望只拿走 1 个元素），而且元素和条目对不上了（原来画“写作业”的元素现在画的是别人）。
- [18]–[25] 写不出来：第二个实例（组件认的是全页唯一的控件名）、自己画的插槽（只能交回一段文字）、放上以后 / 拿走之前（没有“放上”这个时刻）、拿走（最多藏起来，事件处理没处统一取消）、用积木“放”一个组件。

### 2.3 05 完整流程：对两个服务都是 11/15

不过的 4 条（[4][5][8][14]）是同一个原因：`net.fetch` 不成功只交回空。校验没过、同名重复、服务器连不上，前端都只能显示“提交失败”。其余 11 条（合法提交、清空、连点只发一个请求、删除、重新加载、元素没被重建）第 1 轮就过了。

### 2.4 测试中发现的问题（单列，都当场停下查清了）

1. **状态库在 Node 里算错并崩掉（03 第 1 轮）。** 查清的机制：F1 的规矩是“调函数值一律等”，所以派生值的“读”成了要等的。主程序读派生值，算到一半在“等”那里让出；之前排好的“这一段跑完以后做”正好插进这个空当，去读同一个派生值，发现它“正在算”，得到一个假的“派生值绕回了自己”；两边收尾时又把“现在是谁在记依赖”恢复错了，卡在一个派生值上；后面主程序一写状态，就报假的“派生值的算法里不能改状态”。调试时打印出来的原话：`此刻正在跑的： 派生 100005 丁= 100010 乙= 100008 丙= 100009 两倍= 100005`。Python 没有这个问题，因为 Python 那份里没有“让出”。**同一份库，两种语言行为不同，而且错得很隐蔽。**
2. **第 2 轮第一次跑 03，检查全过，但错误输出里多了一行**：`事件“改”的处理出错：这里要一个不用等的函数，可给的函数里有要等的事`。查清：检查程序第 [23] 条的处理函数里用普通方式调了一个“退订函数”，脚本于是把整个处理函数当成“要等的”。把那一处改成 `call!` 后错误输出为空。改的是检查程序的一处调用方式，期望没动。这说明：没有类型的时候，写的人得处处手工标“这个不用等”，漏一处就出事——所以要靠类型自动推。
3. **05 的 `run.sh` 第一次跑有两处脚本自己的错**（一个文件少一个右括号；bash 算术里用了中文名字），改掉后第 1 轮、第 2 轮结果如上。和设计无关，记一笔。
4. 04 第 2 轮、05 第 2 轮都是第一次跑就全过。我回头看了输出确认检查是真的在比（树、操作次数、元素是不是同一个都印出来了），没有发现问题。

## 3. 设计改动（第 1 轮 → 第 2 轮）

| 改动 | 理由 | 落在哪 |
|---|---|---|
| **函数分“不用等的”和“可能要等的”**；库的回调（算法、取值、做法、画法、标识、总线处理）规定为“不用等的”，用 `call!` 调；只有“一起改”的口许等 | 2.4 的第 1 条。响应式要求“读一个值”中途不能让出 | L1、类型 |
| `tick.defer` 的函数不许等 | 同上；宿主也要守这条 | L0 |
| 界面事件的处理、组件发出的事件：**许等，但宿主 / 组件不等它**（“开始做”） | 表单提交要等请求回来；组件不该被外面的处理拖住 | L0、L1 |
| 标准库加 `isSame` | “设成同一个值不触发”要按“是不是同一个”判，对齐 D 写的规矩 | L2 |
| 清单加“懒值”槽 | “当〔这个式子〕变了”——式子要交给库反复算，不能在放积木的地方先算掉 | L3 |
| 加 4 个元素级宿主接口，用积木写画面库 | 2.2。没有它们，重复、存在条件、插槽、多实例、拿走都写不出来 | L0、L3 |
| 发请求换成“请求记录 → 回应记录”，只有网络层失败才出错 | 2.3 | L0 |
| 状态库加“归属”的公开函数“收尾时” | 画面库要把“取消事件处理”“停掉里面的更新”挂到归属上 | L3 |

第 2 轮库里“要等的”函数从 50/105 降到 4/106（03）；整个状态库和画面库没有一处要等。

## 4. 第 2 轮结果

- **03**：Node 48/48、Python 48/48，两边输出逐字节相同，错误输出都是空的。探针（把里面有要等的事的处理函数交给总线）：Node 报“这里要一个不用等的函数…”并被总线接住，后半截以后悄悄做完；Python 照常等完、不报错。两边不一样——这正是要进类型、在编辑时拦的理由。
- **04**：25/25。量到的“只有该变的部分变”：点一条 → 宿主只被要求写 1 次；改一条的完成 → 写 1 次；末尾加一条 → 原来两条的元素没动；删一条 → 只拿走 1 个元素、写 0 次；调顺序 → 没有新建没有拿走、元素还是原来的；拿走组件以后再改它的条目、点它原来的元素 → 宿主一件事都没被要求做。
- **05**：对 Node 服务 15/15、对 Python 服务 15/15，两边前端输出逐字节相同。合法提交列表多一条且输入框清空；非法提交显示服务器说的原因（“title 的长度要在 1 到 20 之间；level 只能是 高、中、低 里的一个”）、列表不变、填的东西还在；同名重复提交服务器回 409，显示“已经有这一条了”、列表不变；连点两下宿主只发出 1 个请求；服务器连不上显示“连不上服务器”。

回答任务的问题：**用“语言核心＋标准库＋最小宿主接口”，能完整组成前端的库、组件和一个完整流程——前提是补上第 3 节那几样。** 不补，状态库在 Node 里写不对，组件写不出来。

## 6. 和 D、C、F1 不一致或需要它们改的

**和 D：**

1. D 明确“不给创建 / 插入 / 删除任意元素”。原型证明这样组件不能由积木封装出来（GAP-F2-05）。要么 D 承认普通网页产物下有元素级接口和一个内置的画面库，要么承认“组件”不在“全靠封装”的范围里。注意：我的画面库只对普通网页成立；导出成 Vue / React 时元素归框架管，这一层还得由导出器翻。
2. D 的状态.新建 / 读 / 写 / 派生 / 监听是 5 个宿主接口。原型里它们是用积木写的一个库，只要 2 个宿主接口（这一段跑完以后做、让攒着的先跑完）。建议普通网页产物里把这 5 个从 L0 挪到 L3（内置库），L0 只留那 2 个。
3. D 附录 A 的小运行时只有状态、派生、跟着做、冲刷。原型多做了：归属和自动收尾（对应 GAP-D-9，证明能用积木做）、100 轮保险、派生绕圈报错、收尾函数、“当…变了”的新旧值、一起改里许等。

## 7. 没跑、没核对的

- **没跑**：真浏览器；Vue / React 产物；PHP、Go、Java。04 和 05 的前端只在 Node 的假页面里跑，没有 Python 的假页面（03 的两个库在 Python 里跑了）。
- **假页面不是浏览器**：没有排版、没有默认行为（“阻止默认行为”是空的）、没有捕获阶段、输入框只有一个“值”。事件只做了从目标往上传和“别再往上传”。
- **原型的简化**：“每一个”“如果有”的画法只能交回一个元素（不能是好几个，不能直接嵌套另一个“每一个”）；调顺序时留下的元素全部重新排一遍（不是最少挪动）；跟着做的事读的派生值没变也会重做一次（03 第 [17] 条，期望里就是这么写的）；输入框的双向绑定没处理输入法。
- **没验证的能力**：组件的方法（外面叫组件做事）、具名插槽以外的“默认插槽”、动态选组件、路由、状态仓库库（D 8.3 的伪代码没有照着写）、表单控件里除了文字输入框以外的（勾选、下拉）。
- **没测的边角**：`isSame` 对“不是数”和正负零；1000 条以上列表的快慢；两个请求先后回来顺序颠倒（只测了“上一个没回来就不发下一个”）；请求超时那条分支（写了，没触发过）。
- **没核对官方文档的**：`isSame` 想对齐的 JS“同一个值”规则的细节；Node 自带 fetch 会拒绝的端口名单（我只是避开了小端口）；Python 那边 F1 宿主的线程模型。
- 05 的后端每次起来都是空的（存储在内存里），没有验证重启后还在。

## 8. 给协调者的清单（需要霜霜拍板，3 件）

1. **回调里能不能“等”。**
   - A（建议）：库的回调默认“不许等”，放了要等的积木就在编辑时提示；想等，自己放一块“开始做”。界面事件和组件事件的处理例外：许等，宿主不等它。
   - B：一律许等（F1 现在的样子）。代价：状态库这类东西在 JS 里写不对。
2. **普通网页里，组件靠什么来。**
   - A（建议）：加 4 个元素级宿主接口，“画面库”做成内置库，组件完全用积木封装（本原型）。Vue / React 导出仍走 D 的导出器。
   - B：维持 D——重复、存在条件、插槽都由导出器生成。代价：组件不是“封装得来”的，用户库里也就做不出像样的组件。
3. **发请求的接口前后端统一成一个**（请求记录 → 回应记录，任何状态码都拿得到回应）。建议：统一，F1 的 `net.fetch` 退掉。不统一的代价：前端显示不了服务器说的原因。
