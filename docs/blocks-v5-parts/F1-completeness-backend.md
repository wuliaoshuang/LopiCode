## 0. 结论摘要

**问题**：只靠“语言核心的积木＋标准库＋一小撮宿主原生接口”，能不能完整搭出一个库、完成一个完整流程？

**回答：能，但要先补上几样东西。** 这不是纸面推出来的：两个库都真的写了、翻成 Node 和 Python 真的跑了。

1. **库“接口服务”（把现有全部后端积木改写成库）**：路由、请求、响应、数据集合全部用核心写成，约 235 行。产品现有一致性样本的**全部 135 条**请求，Node 135 条、Python 135 条都等于产品测试里写死的期望，两种语言逐字节相同。**只用第 4 版的核心（第 1 轮）就全过了。**
2. **库“小框架”（路由分组、洋葱中间件、带状态码的错误类、校验助手）**：用类、继承、接口、闭包、试着做 / 抛出写成，约 390 行。事先写好期望的 **39 条**请求：第 1 轮两种语言都是 38 条通过，第 2 轮都是 39 条通过，两边逐字节相同。
3. **现有 12 种语句、22 种值的去处**：15 块变成库的积木，19 块本来就是语言核心（设变量、如果、重复、运算、连起来……），不需要库。对照表在第 6 节。

**“加上这几样就能”的“这几样”**（按要紧程度）：

- **必须有、第 4 版没定清的**（没有它们第 1 轮都写不出来）：
  - 一个内置的“错误”类，“抛出”要能抛对象（GAP-F1-01）。没有它，错误带不了状态码。
  - 积木的定义不能只有“调一个函数”：还要“调对象的方法”“调类的静态方法”“一段模板”（GAP-F1-02）；还要能用外层帽子积木提供的“隐含的东西”，比如“请求”（GAP-F1-04）。
  - 宿主要约定“所有启动的事做完，才开始收请求”（GAP-F1-11）。
- **第 1 轮写出来了但结果错或很别扭、第 2 轮补上的**：
  - 标准库加 2 个函数：“是不是数字写法”（GAP-F1-07，第 1 轮唯一没过的那条请求就因为它）、“空就用另一个”（GAP-F1-08）。
  - 宿主接口加 3 个：`store.update`（GAP-F1-12）、`time.ms`（GAP-F1-13）、`log.error`（GAP-F1-14）。
- **第 2 轮自己撞出来、现在只是绕过去、要在类型系统里真解决的**：
  - **“一个函数要不要等”必须是函数类型的一部分**（GAP-F1-09）。第 2 轮改用 `store.update` 后，同一份程序 Python 全过、Node 出错，原因就是这个。现在靠翻译脚本的硬规矩绕开，但还留着一个洞（实测：同一段程序 Node 得 `[1,2,3,4]`，Python 得 `[3,4]`）。
  - **对象不能交给标准库**（GAP-F1-05）。实测：把对象变成 JSON，Node 输出了内部字段，Python 直接出错。

**数字**：缺口一共 **24 条**（GAP-F1-01 到 24）。按主要影响的那一层算：L0 有 7 条、L1 有 8 条、L2 有 4 条、L3 有 5 条（有几条同时牵涉类型系统）。原型里已经补上并跑通的 11 条；凑合绕过去、设计里要正式定的 5 条；只记下来没动的 7 条；加了但没用上的 1 条。

**核心被迫加的东西，全部列在这里**：内置类“错误”；标准库函数 `isNumeric`、`orElse`、`typeName`；语句“原样再抛出”；宿主接口 `store.update`、`time.ms`、`log.error`。其中 **`typeName` 和“原样再抛出”加了但两个原型最后都没用上**——不算被证明必要。

**没做 / 没跑的**：Go、Java、PHP 没做（这一轮不要求，机器上也没有 php）。类型检查没做（翻译脚本不带类型）。真机没跑。“两个请求同时改数据会撞”是按道理推的，试了几次**没实测撞出来**。

**要霜霜拍板的 3 件**在文末清单里。

## 1. 文本形式和翻译脚本

### 1.1 是什么

- **文本形式**：用 S 表达式把语法树写成文字，一个节点一对括号，比如 `(if (when (> n 3) (return "大")) (else (return "小")))`。节点和第 4 版设计稿第 4.2 节那张表一一对应。完整语法在 `tool/README.md` 第 2 节。
- **翻译脚本** `tool/lcx.py`（Python 写的，只用自带的东西，约 1850 行）：读文本形式 → 把库的积木展开成核心写法 → 检查（名字找不找得到、参数个数、类和接口）→ 生成能直接跑的 Node 代码和 Python 代码。
- **标准库（L2）直接用产品现成的小库**：从 `lib/backend/runtime_*.dart` 原样抄出来，一个字没改（产品版本 master cc7c7e2）。这样“值的规矩”（数字一律小数、整数显示不带小数点、除以 0 得 0、字典按键排序输出）天然和产品一致。只用了其中的值的规矩和标准库函数，**没用**它手写的路由、请求、集合那部分——那部分正是要用核心重写的。

### 1.2 它是一次性的验证工具，不是产品的生成器

它只为回答“核心够不够”。所以：只翻 Node 和 Python；不带类型检查；生成的代码不讲究好看和快；出错提示只到“哪个文件哪一行”。产品要用的是 `lib/lang/` 里的正式生成器。

### 1.3 怎么保证没有偷偷加东西

脚本里有三张“只许用这些”的表：节点、标准库函数（照 `lib/lang/rt.dart` 的两张表）、宿主接口（`tool/natives.json`）。表以外的东西单独登记，并标上缺口编号和“第几轮加的”。用 `--round 1` 翻译时，用到第 2 轮才加的东西会直接报错。每次翻译完会打印并存下统计（`out/*/report.txt`），其中一行就是“核心表以外、被迫加的”。第 1 轮两个库这一行都是“无”。

有一样东西不在这张统计里、但第 1 轮就用了：内置的“错误”类（见 GAP-F1-01）。

### 1.4 自测

`tool/selftest/features.lcx` 把语言特性走了一遍（默认参数、剩余参数、闭包、递归、各种循环、类 / 继承 / 接口 / 抽象方法 / 静态 / 私有、自定义错误、试着做的各种组合、各种运行时错误的消息、同时做两件事）。**跑过**：Node 和 Python 的 36 行输出逐字节相同，并且等于事先手写的期望。

自测没覆盖到的：“原样再抛出”没有任何地方跑过；`isNumeric`、`orElse` 只在两个原型里用到；`typeName` 只在探针里跑过。

### 1.5 局限（会影响怎么读这份结论）

1. **没有类型检查**。所以“类型上说不清的地方”是我写的时候觉得说不清，不是检查器报出来的。
2. **“要不要等”是脚本猜的**（规则见 GAP-F1-09），有一个已知的洞。
3. **变量是函数级的**：循环里做的闭包记住的是变量本身，不是那一圈的值。两种语言一致（自测里三个闭包都输出 3），但 Go / Java 里不一定天然如此——没跑，不知道。
4. **`是不是某个类` 只认类，不认接口**；私有字段只按名字粗查。
5. 库的“公开了什么”没有按清单再筛一遍：用了库就看得见它所有模块标了“公开”的东西。

## 2. 宿主原生接口（L0）：最终清单和细则

Node 和 Python 各实现了一份（`tool/host_node.js` 162 行、`tool/host_python.py` 171 行），真的开 HTTP 服务，只用自带的东西。

### 2.1 清单（10 个）

| 接口 | 参数 → 结果 | 要等吗 | 哪一轮 |
|---|---|---|---|
| `http.serve` | (端口, 处理函数) → 空。每来一个请求调一次 处理函数(请求)，它返回一个响应 | 否 | 1 |
| `store.get` | (名字) → 值；没存过得空 | 否 | 1 |
| `store.set` | (名字, 值) → 空 | 否 | 1 |
| `store.update` | (名字, 函数) → 结果。函数(旧值) 要返回 `[新值, 结果]` | 否；**函数里也不许等** | 2 |
| `url.decode` | (文字) → 文字 | 否 | 1 |
| `url.encode` | (文字) → 文字 | 否 | 1 |
| `net.fetch` | (方式, 网址, 数据) → 文字或空 | **要** | 1 |
| `time.sleep` | (毫秒) → 空 | **要** | 1 |
| `time.ms` | () → 数字（从 1970-01-01 起的毫秒数） | 否 | 2 |
| `log.error` | (值) → 空。文字化后写一行到错误输出 | 否 | 2 |

任务书里说的“打印、现在的时间、JSON 互转”没有做成宿主接口——它们已经是标准库函数了（`log`、`now`、`toJson`、`fromJson`），直接用。`url.encode` 实现了，但两个库最后都没用到。

### 2.2 `http.serve` 必须写死的细则

这些是写的过程中一条条撞出来的：不定死，两种语言就不一样，或者库没法做到和现有小库行为一致。

**什么时候开始收请求**
1. `http.serve` 只是登记，不马上开始收请求；一个程序只能登记一次。**所有模块“启动时”要做的事都做完以后**，宿主才开始监听。原因：Node 里监听不卡住，Python 里监听会一直卡住——不这么约定，Python 里写在“开始服务”后面的积木永远不会做（GAP-F1-11）。
2. 端口：先看环境变量 `PORT`，没有才用程序里给的；地址看 `HOST`，默认 `0.0.0.0`。开始监听后在标准输出打一行 `后端已启动：http://地址:端口`（和现有小库一样）。

**请求（一个字典，五个键）**
3. `method`：请求行里写的方式，原样。
4. `path`：问号前面的部分，**原样不解码**；`query`：问号后面的部分，原样。拆段、解码是库的事（现有小库的规矩是“先按 `/` 切再每段解码”，交给库才做得到）。
5. `headers`：字典。名字一律变小写；同名的头按出现顺序用 `, ` 连起来；值去掉两头的空格和制表符。实测 `X-Test: a` 加 `x-test: b`，两种语言都得到 `a, b`。Node 这边特意用“原始的头列表”自己合并——因为 Node 自己合并时，有一批头（`authorization`、`content-type`、`host` 等）遇到重复会直接丢掉后面的，和 Python 不一样（已对官方文档核对）。
6. `body`：文字。请求内容按 UTF-8 解码；**不是合法 UTF-8 就得空文字**；开头的 BOM 保留。没有“字节”这种值（GAP-F1-15）。
7. 请求内容上限 1MB，超了宿主直接回 413，不调处理函数。回的内容是 `{"error":"请求内容太大"}`（和现有小库一样）。这一条现在是宿主写死的，库管不了。

**响应（一个字典，三个键）**
8. `status`：数字，100–599；不在范围里宿主回 500。
9. `headers`：字典，库全权决定，宿主按键排好序写出去。**宿主只自己补一个 `Content-Length`**，不用分块传输。
10. `body`：文字，按 UTF-8 写出去。状态码是 204、304 或 1xx 时不写内容也不写 `Content-Length`；请求方式是 HEAD 时不写内容。
11. 处理函数把错抛到了宿主：回 500，原因写到错误输出。
12. 处理函数可以“要等”：宿主会等它返回。

**两种语言之间还留着的差别**
13. 同时来的请求：Node 是一条线轮流做；Python 是每个请求一条线。所以“同时改同一份数据”在两边不是一回事（GAP-F1-12、GAP-F1-19）。
14. 不认识的请求方式（实测发了一个 `FOO /`）：Node 回 400、没有内容；Python 回 501、一页英文网页。两边都没进到库里。Python 的宿主只接 GET、POST、PUT、PATCH、DELETE、OPTIONS、HEAD（GAP-F1-21）。

### 2.3 `store` 的细则

1. **按值存取**：放进去的是一份拷贝，拿出来的也是一份拷贝。拿出来改了不放回去，等于没改。原因：不这样的话，Node 里拿出来直接改就生效、别的宿主（数据放在文件或数据库里）不生效，行为不一样。代价见 GAP-F1-12 的说明：整个集合每次读都拷一遍，数据多了会慢。
2. `store.update(名字, 函数)`：宿主保证“取旧值 → 调函数 → 放新值”中间没有别的请求插进来。函数里不能有要等的事（Node 里函数返回了“稍后的结果”就报错）。Python 里用一把锁。
3. 值只能是能变成 JSON 的东西（数字、文字、是否、空、列表、字典）。对象放不进去。

### 2.4 其他几个

- `url.decode`：百分号解码；写法不对（`%` 后面不是两位十六进制）或者解出来不是合法 UTF-8 → 原样返回；不动加号（加号变空格是“网址参数”那一层的事，库自己做）。
- `url.encode`：按 UTF-8，字母、数字和 `- . _ ~` 原样，其余每个字节写成 `%XX`（大写）。
- `net.fetch`：直接用现有小库的实现和规矩——成功（2xx）得到响应的文字，其余一律得空，最多等 10 秒。
- 宿主自己出的错（比如 Node 的 `TypeError`、Python 的 `KeyError`）消息两种语言不一样。被“出错了”接到时，统一换成一句 `运行时内部出错`，原来的消息丢掉（GAP-F1-23）。

## 3. 两轮各发现了什么、改了什么

### 3.1 第 1 轮：只用第 4 版的核心

**结果**（跑过，`run_all.sh` 里每次都重跑第 1 轮的快照）：

| | Node | Python | 两边互比 |
|---|---|---|---|
| 01 接口服务 | 135 / 135 | 135 / 135 | 134 条逐字节相同，0 条不同（另 1 条是“现在的时间”，只核对格式） |
| 02 小框架 | 38 / 39 | 38 / 39 | 39 条逐字节相同（错也错得一样） |

用了多少东西：01 用了 29 种节点、25 个标准库函数；02 用了 34 种节点、26 个标准库函数。“核心表以外被迫加的”：两个都是 0 个标准库函数、0 个节点。

**没过的那一条**：02 的第 17 条 `GET /api/books/1.0`，期望找到 1 号书（200），实际回 400“id 要是数字”。原因是 GAP-F1-07。

**卡住的地方**（按任务书要求的几类分）：

*节点不够*
- “抛出”只能带一段文字，抛不了带状态码的东西；也没有内置的“错误”类可以继承（GAP-F1-01）。这一条绕不过去，第 1 轮就先加了。
- 一个“试着做”只有一个“出错了”的口，口上只能指定一个错误类。要“HTTP 错误变成对应响应、别的错误变成 500”，只好写两个中间件类套起来（GAP-F1-06）。
- 接到错误以后没法“原样再抛出去”（GAP-F1-03）。

*标准库函数不够*
- 分不清 `"0"` 和 `"abc"`：“数字化”都得 0（GAP-F1-07）。
- “空就用另一个”要写三句（GAP-F1-08）。
- 没有“截掉小数”，状态码取整用了“向下取整”代替（对正数一样；负数不一样，但负数本来就不在 200–599 里）。
- 没有正则。路径匹配、网址参数解析都是手写的切分——写得出来，没有卡住（GAP-F1-22）。

*外观机制表达不了的*
- “请求别的网址”有两个内联口（成功时 / 失败时），而且可以把结果放进变量。它没法定义成“调一个函数”，只能是一段模板（GAP-F1-02）。
- “路径参数”“请求头”这类积木要用到外层“当收到请求”提供的“请求”，但用户不该看见、不该填。第 4 版设计稿第 5.2 节没写这种“隐含的东西”怎么传（GAP-F1-04）。
- 框架库的积木“当收到 GET /x 时”展开成的是“调某个对象的方法”，不是调函数；“回复 JSON”展开成调类的静态方法（GAP-F1-02）。
- 收尾型积木的毛病：放在内联口里，结束的是外面那个接口（对的）；放进嵌套的回调口里，结束的只是那个回调（GAP-F1-17）。
- “往集合里加”有个可选的“结果放进变量”——这其实是任何有结果的语句型积木都可能要的（GAP-F1-24）。
- 旧文档里不是积木的东西没地方放：端口、“有哪些数据集合”、“每次请求从初始值开始的变量”（GAP-F1-18）。

*原生接口不够或语义不清*
- `http.serve` 卡不卡住没说（GAP-F1-11）。
- `store.get` / `store.set` 是“拿出来的是原件还是拷贝”没说；“取出来 → 改 → 放回去”是三步（GAP-F1-12）。
- 没有毫秒级的时间（GAP-F1-13）、没有“写到错误输出”（GAP-F1-14）、没有字节（GAP-F1-15）。

*类型上说不清的*
- 请求、响应是字典，键名写错（比如把 `status` 写成 `statsu`）没有任何东西能查出来（GAP-F1-16）。
- 函数当值传来传去以后，不知道它“要不要等”（GAP-F1-09）。
- 对象交给标准库会怎样没定义（GAP-F1-05）。

*两种语言不一致的*
- “创建时”里不能等（JavaScript 的规矩，已核对；Python 没这个限制）（GAP-F1-10）。
- “开始做”在 Node 里是轮流、在 Python 里是真的同时（GAP-F1-19）。自测里撞到过：两件事各睡几毫秒，Python 那边先后顺序和 Node 不一样，把睡的时间拉开才稳定。

### 3.2 我提的“核心怎么改”（一组具体的增补）

| # | 增补 | 层 | 对应缺口 |
|---|---|---|---|
| 1 | 内置类“错误”（字段：消息）；“抛出”收任何值：是“错误”对象就抛它，别的值文字化后包成“错误” | L1 | 01 |
| 2 | 标准库函数 `isNumeric(值)`：这个值是不是数字、或者是一段“数字写法”的文字 | L2 | 07 |
| 3 | 标准库函数 `orElse(值, 默认)`：值是空就得默认 | L2 | 08 |
| 4 | 宿主接口 `store.update(名字, 函数)` | L0 | 12 |
| 5 | 宿主接口 `time.ms()`、`log.error(值)` | L0 | 13、14 |
| 6 | 不加新积木：“出错了”口里用“是不是某个类”分开处理各类错误（代替多个口） | — | 06 |
| 7 | 翻译规则：直接传给“不会等的地方”的匿名函数，按“不许等”翻；里面真有要等的事就报错 | 类型 | 09 |
| 8 | 积木定义四种：调函数 / 调方法 / 调静态方法 / 模板；可以引用隐含参数 | L3 | 02、04 |
| 9 | 宿主约定“启动的事都做完才开始收请求” | L0 | 11 |
| 10 | 语句“原样再抛出”、标准库函数 `typeName(值)` | L1、L2 | 03、05 |

第 8、9 条其实第 1 轮就已经这么做了（不这么做写不出来），这里是把它正式提出来。

### 3.3 第 2 轮：按改过的核心重写受影响的部分

**重写了什么**：
- 01：`集合` 模块——加、改、删改用 `store.update`；默认值改用 `orElse`。别的没动。
- 02：`校验` 的“要数字”改用 `isNumeric`；`仓库` 改用 `store.update` 和 `orElse`；`错误处理` 和 `兜底` 两个类合成一个（一个口里用“是不是某个类”分支），默认把 500 的原因写到错误输出；示例服务的记日志中间件用 `time.ms` 算耗时。

**结果**（跑过）：

| | Node | Python | 两边互比 |
|---|---|---|---|
| 01 接口服务 | 135 / 135 | 135 / 135 | 134 条逐字节相同，0 条不同 |
| 02 小框架 | 39 / 39 | 39 / 39 | 39 条逐字节相同；日志 39 行也等于期望 |

用了多少东西：01 用 29 种节点、26 个标准库函数（多了 `orElse`）、5 个宿主接口；02 用 34 种节点、28 个标准库函数（多了 `isNumeric`、`orElse`）、7 个宿主接口。

**第 2 轮新发现的两件事**：

1. **改用 `store.update` 以后，同一份程序 Python 全过、Node 出错。** 原因：翻译脚本的规矩是“调函数值一律等”，于是传给 `store.update` 的那个匿名函数（里面又调了别的函数值）在 Node 里被翻成了“要等的”，宿主拿到的是“稍后的结果”而不是新值。Python 里“等”什么都不用做，所以没事。修法就是上表第 7 条。当时 Node 具体错了几条没有留下记录。
   这件事说明：**“要不要等”光靠翻译时猜是不够的，必须进类型**。我又专门写了一个探针（`tool/probes/async_predicate.lcx`，跑过）：把一个“要等的”有名字的函数交给标准库的“筛选”，Node 得 `[1,2,3,4]`（错的），Python 得 `[3,4]`（对的）——这个洞现在还在。
2. **“原样再抛出”加了，但没用上。** 错误处理改成“一个口里分支、自己兜底”以后，不需要再抛。`typeName` 也没用上。所以这两样**没有被证明是必要的**，建议先不进核心。

### 3.4 第 2 轮以后还剩什么没解决

## 5. 结论：只靠核心能不能搭出库

**加上这几样就能。**

- **能的证据**：两个库约 620 行文本形式，没有一行“原生片段”；除了 10 个宿主接口，其余全部是语言核心节点和标准库函数。跑通的请求 135＋39 条，两种语言逐字节相同。
- **“这几样”是什么**：第 0 节已经列了。最少的一组是：内置“错误”类（01）、积木定义四种写法加隐含参数（02、04）、宿主“做完启动才开门”（11）、`isNumeric`（07）、`store.update`（12）。其余是“有了好写很多”。
- **不能光看“跑通了”的地方**：
  1. 跑通靠的是翻译脚本的两条硬规矩（“要不要等”怎么猜、对象不交给标准库）。换成类型检查之前，用户很容易写出“一种语言对、另一种语言错”的程序（09、05 都有实测的反例）。
  2. 只验了 Node 和 Python。这两种都是“变量不用写类型、字典随便用”的语言。Go 和 Java 要写类型——字典当记录用（16）在那边会更难。**没跑，不知道**。
  3. 库是我一个人顺着写的，没有另一个人拿着清单来用。库格式的字段够不够，要和 C 的纸面设计对过才知道。

| `exports.functions` / `classes` / `interfaces` | 公开了什么 | 原型**没有**按它筛（局限第 5 条） |
| `lists` | 库声明的“项目清单”种类（比如“数据集合”） | “清单”种类的槽没地方选 |
| `context` | 库有哪些“隐含的东西”（比如“请求”）、由哪块积木的哪个口提供 | 值型积木不知道能不能放在这里 |
| `blocks[]` | 每块积木：`id`、`name`、`shape`、`text`（积木上的文字，槽用占位）、`slots`、`needs_context`、`def`、`replaces`、`doc` | — |
| `blocks[].slots[]` | `name`、`kind`（值 / 选项 / 清单 / 变量 / 回调口 / 内联口）、`optional`、`choices`、`list`、`params` | — |
| `blocks[].def` | 展开成什么：调函数（可带“放进变量”）/ 调方法 / 调静态方法 / 模板 | — |
| `blocks[].replaces` | 这块积木顶替旧文档里的哪种积木 | 旧文档没法自动搬到新库 |

**遇到的问题**

1. **积木的定义放哪**。我放在清单里（JSON）。好处是不用读模块就知道库有哪些积木；坏处是定义和它调的函数分在两个文件里，改了函数的参数容易忘改清单——原型里就靠翻译时报“参数个数不对”才发现。
2. **模板是单独的文件**（`.tpl`），里面是文本形式加几个占位记号。它不是函数，没法单独检查对不对，只有被用到、展开以后才知道。
3. **槽没有类型**。清单里槽只有“种类”，没写“要数字还是要文字”。类型系统做出来以后这里要加。
4. **“隐含的东西”占名字**：口提供的“请求”会和用户自己起的同名变量撞。要么展开时自动改名，要么编辑时拦。
5. **旧文档怎么搬**。`replaces` 只够一对一的。旧的“对象＋键值对”两块变成一个字典、旧的“接口”变成帽子积木——这些要专门的搬迁规则，清单里一个字段写不下。
6. **库的版本和核心的版本是两回事**。第 2 轮库的 `requires.core` 写的是“第 4 版加增补”。库清单要能写“最低要哪一版核心、要哪几个增补的标准库函数”，否则旧应用读到新库会出莫名其妙的错。
7. **宿主接口的“轮次”**也一样：`store.update` 是后加的，库要能写明“需要 `store.update`”，装库的时候宿主没有就直接说“这个库用不了”，而不是跑到一半出错。这一点 `requires.natives` 已经能表达。
8. **库的“启动时”**。两个库都没有需要在装上时自己跑的代码；但“接口服务”的路由表是一个模块级的变量，谁先谁后初始化要有规矩（原型：按依赖顺序，被用的先）。

## 给协调者的清单

### 缺口（24 条，详见第 4 节）

- **要在第 5 版设计里定的 9 条**：GAP-F1-01（内置错误类）、02（积木定义四种写法）、04（隐含参数）、05（对象和标准库）、09（“要不要等”进类型）、10（“创建时”不许等）、11（宿主“做完启动才开门”＋上限做成选项）、16（记录类型和函数类型）、18（项目清单和配置项）。
- **已经补上并跑通、建议直接收进核心的**：07（`isNumeric`）、08（`orElse`）、12（`store.update`）、13（`time.ms`）、14（`log.error`）、06（不加东西）、23、24。
- **建议先不加的**：03（“原样再抛出”）和 `typeName`——加了，没用上。
- **记下来、这一轮不用动的**：15（字节）、17（收尾型进嵌套口，要在编辑时拦）、19（“开始做”的先后）、20（接口认不认）、21（请求方式）、22（正则）。

### 和现有设计（第 4 版设计稿、现有代码）不一致的地方

我没读到第 5 版的设计骨架文件，下面是和第 4 版设计稿、`lib/lang/` 现有代码对不上的地方：

1. 设计稿说“自定义错误＝继承内置错误类”，但 `lib/lang/ast.dart` 里“抛出”节点只带一段消息文字，也没有内置错误类。（GAP-F1-01）
2. `lib/lang/ast.dart` 里有一个 `LHost` 节点，设计稿第 4.2 节的表里没有。我没用它。
3. 设计稿第 6.1 节的最小原生接口 `http.serve`、`store.get` / `store.set` 不够：少了第 2.2、2.3 节那些细则，也少 `store.update`。
4. 设计稿第 5 节的封装只讲了“一块积木＝一个函数”，没讲模板型、调方法型、隐含参数。
5. 现有小库把状态码“截掉小数”，标准库函数表里没有“截掉小数”，我用“向下取整”代替——在 200–599 这个范围里结果一样。

### 要霜霜拍板的（3 件）

1. **“要等的事”要不要让用户看见？**
   - A（建议）：用户不用管，系统自动推断；只有在“把一个要等的函数交给不会等的地方”时，编辑器拦下来并用大白话说明。
   - B：积木上明着标“这块要等”，用户自己放“等”积木。
   - 建议 A 的原因：现有后端积木的用户从来没见过“等”，B 会让“请求别的网址”这种常用积木变难用。A 的代价是类型系统要多做一块（GAP-F1-09）。
2. **“同时做几件事”（开始做）承诺到什么程度？**
   - A（建议）：只承诺“各种语言最后结果一样”，不承诺谁先谁后；要同时改同一份数据，只能走宿主提供的“一口气改完”。
   - B：承诺先后也一样——那 Python、Go、Java 都只能假装一条线轮流做，慢而且实现麻烦。
3. **现有后端积木改成库以后，旧文档里“每次请求都从初始值开始的变量”还要不要？**
   - A（建议）：保留这个行为，做成帽子积木的“每次进来先做的事”，旧文档搬过来行为不变。
   - B：改成普通的变量（服务启动后一直留着）——更像真的编程语言，但旧文档的行为会变。

### 没核对、没跑成、看不出来的

- **没做**：Go、Java、PHP 的翻译和运行（这一轮不要求；机器上没有 php）。没有 tsc，没生成 TypeScript。
- **没做**：类型检查。
- **没跑**：`flutter test`、`tool/check.sh`（按规矩不跑）；真机；和产品现有生成器的生成物直接比。
- **没实测复现**：“同时加数据会撞号”（GAP-F1-12）。同时发 30 个请求试了几次都没撞；同时发 60 个那次探针自己卡住了，被我停掉，没有结论。
- **没留下记录**：第 2 轮改用 `store.update` 后 Node 具体错了几条。
- **没验证**：库依赖别的库（`requires.libs`）；清单的 `exports` 真的起筛选作用；两个库同时用在一个程序里。
- **没核对官方文档的**：Python 遇到不认识的请求方式回 501（只是实测到了，文档里没找到这句话）；Node 遇到不认识的请求方式回 400（只是实测到了）；Python 里把请求内容按 UTF-8 解码、Node 里解码器的“不合法就报错”选项（照着自己的理解写的，行为靠 135 条样本里那几条不合法内容的请求验证过）。
- **版本对不上的**：核对的 Node 文档是 v26 的页面，机器上跑的是 v24.22.1；Python 文档是 3.15 的页面，机器上是 3.12.3。核对的那几条都是很早就有的行为，但我没有去翻 v24 / 3.12 的页面再对一遍。
- **看不出来的**：这套东西在 Go / Java 这类要写类型的语言上会多出多少缺口。
