# 01-backend-lib —— 把现有全部后端积木改写成库“接口服务”

**一句话结果**：库全部用语言核心写成（路由、请求、响应、数据集合都不再是手写在小库里的），用它搭的示例服务在 Node 和 Python 上各打了产品现有一致性样本的**全部 135 条请求**，**135 条都等于产品测试里写死的期望**，两种语言之间逐字节相同。第 1 轮（只用积木第 4 版的核心）就全过了。

## 怎么跑

```
bash 01-backend-lib/run.sh        # 在 docs/blocks-v5-prototypes/ 下；要 node 和 python3
```

它做的事：翻译 → 起 Node、Python 两个服务（端口 18101–18122，只听 127.0.0.1）→ 发 135 条请求 → 比对 → 按 pid 关掉服务。两轮都跑。

## 跑出来什么（2026-11-25 真实输出，全文在上一层的 RESULT.txt）

```
[01 接口服务·第1轮] node：135 条请求，135 条等于写死的期望，0 条不等
[01 接口服务·第1轮] node：标准输出 1 行，等于期望的 1 行
[01 接口服务·第1轮] python：135 条请求，135 条等于写死的期望，0 条不等
[01 接口服务·第1轮] python：标准输出 1 行，等于期望的 1 行
[01 接口服务·第1轮] node 和 python 逐条比（状态码＋响应头＋内容，逐字节）：134 条相同，0 条不同
[01 接口服务·第1轮] 结果：全部通过
[01 接口服务·第2轮] node：135 条请求，135 条等于写死的期望，0 条不等
[01 接口服务·第2轮] python：135 条请求，135 条等于写死的期望，0 条不等
[01 接口服务·第2轮] node 和 python 逐条比（状态码＋响应头＋内容，逐字节）：134 条相同，0 条不同
[01 接口服务·第2轮] 结果：全部通过
```

- “134 条相同”：135 条里有一条 `/now`（现在的时间）每次不一样，只用格式核对，不参加两边互比。
- “标准输出 1 行”：样本里“打印”积木打出的那一行 `日志：1.5 {"k":"v"}`，和产品测试期望的一样。
- 比的是什么：状态码、`Content-Type`、内容逐字节；不许分块传输；`Content-Length` 要对得上。两种语言互比时还比全部响应头（宿主自己加的 `Date`、`Server`、`Connection` 除外）。

## 验收样本从哪来

`cases.json`＝产品测试 `test/support/backend_conformance.dart` 里 `conformanceCases` 的全部 135 条，用 `make_cases.py` 机械转过来（只换写法，不改请求和期望；产品文件只读）。**没有跑 `flutter test`**——比的是产品测试里写死的期望值，所以等于和现有小库的行为做了对比。

没有一条对不上。有一条要说明：**`/holes`**。旧文档里这个接口故意放了“读不懂的积木、没声明的变量、不存在的集合”，产品的生成器把它们降级成“空”或“什么都不做”。那是“读旧文档时容错”这一步的行为，不是库的行为，所以示例服务里是照降级后的结果手写的（比如没声明的变量直接写成空）。这条通过不能算对库的验证，只说明“降级以后的样子，库表达得出来”。

## 对照表：现有每块后端积木 → 库调用

现有后端积木一共 **12 种语句、22 种值**。改写后分两类：**15 块变成库“接口服务”的积木**（各自展开成对库里一个函数的一次调用，“请求别的网址”展开成一段模板）；**19 块根本不用库**——它们就是语言核心的积木。另外库多了 2 块原来没有的积木，对应旧文档里“接口”和“端口”这两样不是积木的东西。

“请求”＝外层“当收到请求”那块帽子积木的口提供的隐含参数，用户看不见、不用填。

### 语句（12）

| 现有积木 | 改写后 | 展开成 |

### 原来不是积木、现在是库积木的（2）

| 原来 | 现在 |
|---|---|
| 文档里的一个“接口”（方式＋路径＋一串积木） | 库积木 `当收到请求`（帽子型，一个回调口，口提供“请求”）→ `(do (call 注册 方式 路径 (fn (请求) …)))` |
| 文档里的“端口” | 库积木 `开始服务`（语句型）→ `(do (call 开始服务 端口))` |

旧文档的另外两样也有了去处：**“数据集合”清单** → 项目清单 `(project-list 数据集合 "todos" "notes")`，“清单”种类的槽只能从里面选；**“变量”（每次请求从初始值开始）** → `(hat-prelude …)`，放进每个接口回调的最前面。

## 两轮分别是什么

- **第 1 轮**（`round1/`）：只用积木第 4 版的核心＋`store.get` / `store.set`。135 条全过。
- **第 2 轮**（`libs/`）：只动了“集合”模块——改数据的三件事（加、改、删）从“取出来 → 改 → 放回去”三步，换成新加的宿主接口 `store.update`（一口气做完，别的请求插不进来）。135 条全过。

为什么要改：第 1 轮的写法在“每个请求一条线”的宿主（Python）上，两个请求同时加东西，按道理可能撞号或丢一条。**但这次没实测撞出来**：`race_check.py` 同时发 30 个“加一条”，第 1 轮的 Python 服务试了几次都是“没丢没撞”。所以这条缺口是按道理推出来的，不是实测复现的——如实写在这里。

## 写这个库时发现的事（细节在总文档）

1. 一块积木的定义只有“调一个函数”不够：`请求别的网址` 有两个内联口，只能是模板。
2. `路径参数` 这类积木要用外层帽子积木的“请求”，第 4 版设计稿没写这种“隐含的东西”怎么传。
3. 收尾型积木放在内联口里结束的是外面那个接口（对的）；要是放进嵌套的回调口里，结束的只是那个回调（会让人意外）。
4. `http.serve` 在 Node 里不卡住、在 Python 里卡住——必须约定“所有启动的事做完以后才开始收请求”。
5. 请求里没有“字节”这种值：不是合法 UTF-8 的请求内容只能当“没提交”。
