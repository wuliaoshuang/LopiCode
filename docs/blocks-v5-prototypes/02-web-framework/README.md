# 02-web-framework —— 用语言核心搭一个小型 Web 框架库“小框架”

**一句话结果**：路由（分组、前缀）、洋葱模型的中间件、带状态码的错误类和统一错误处理、请求校验助手——全部用类、继承、接口、闭包、“试着做 / 抛出”写出来了。用它搭的“小书店”服务，事先写好 39 条请求的期望，**第 2 轮在 Node 和 Python 上都是 39 / 39，两边逐字节相同**。第 1 轮（只用积木第 4 版的核心）是 38 / 39，没过的那一条正好指出了标准库的一个缺口。

## 怎么跑

```
bash 02-web-framework/run.sh      # 在 docs/blocks-v5-prototypes/ 下；要 node 和 python3
```

翻译 → 起 Node、Python 两个服务（端口 18201–18212，只听 127.0.0.1）→ 发 39 条请求 → 比对 → 按 pid 关掉。两轮都跑。

- 期望是**第一次起服务之前**写下的（`cases.json`、`expected-logs*.json`），之后没为了让它通过改过期望。

## 这个库有什么（`libs/小框架/`，七个模块，约 390 行文本形式）

| 模块 | 里面是什么 | 用到的语言特性 |
|---|---|---|
| `错误们` | `HTTP错误`（继承内置的“错误”，带状态码和详情）和它的子类：`请求不对` 400、`未授权` 401、`没有这个` 404、`方式不对` 405、`校验没过` 422 | 类、继承、调父类的“创建时”、参数默认值、可改写的方法 |
| `响应` | `响应` 类：状态码、头、内容；`加头` 返回自己好连着写 | 类、静态方法 |
| `上下文` | 一次请求带着走的东西：方式、路径、路径参数、网址参数、请求头、请求内容（用到才解析）、`数据`（中间件往里放东西给后面用） | 类、私有字段 |
| `中间件` | 接口 `中间件`；`串起来`（把一串中间件套成洋葱）；现成的 `错误处理` | 接口、闭包、匿名函数、试着做、是不是某个类 |
| `路由` | `路由器`（前缀、分组、各组自己的中间件）和 `应用`（继承路由器，接到宿主上） | 继承、递归、抛出 |
| `校验` | `校验器`：`必填`、`文字`、`数字`、`其中之一`，最后 `检查`——问题收齐了一起抛 | 闭包（每条规则记住自己的字段名和范围）、函数当值存进列表 |
| `仓库` | 一类东西的增删改查，数据放 `store` | 匿名函数当参数 |

洋葱模型三件事都做到了：**提前返回**（“预检”中间件遇到 OPTIONS 不往里走）、**改请求**（“鉴权”把用户放进上下文）、**处理后改响应**（“记日志”给每个响应加 `X-Request-Id`；作者分组的中间件加 `X-Group`）。

## 示例服务“小书店”（`app/main.lcx`）

- 最外层中间件：记日志 → 错误处理 → 预检
- `/api` 分组：鉴权中间件；资源一“书” `/api/books`（列表、新建、取、改、删）；资源二“作者” `/api/authors`（再下一层分组，有自己的中间件）
- 出错路由：`/boom`（抛一段文字）、`/boom/teapot`（抛自己定义的错误类 418）、`/boom/lib`（标准库抛的错）
- 要等的：`/slow`（睡 30 毫秒）、`/parallel`（同时开始两件事再等它们）
- `/hello/:name`：用库的积木外观写的（帽子型＋收尾型＋要用隐含“上下文”的值型）
- 自己定义了两个错误类 `不许`（403）、`茶壶`（418），都继承库里的 `HTTP错误` 并改写了“变成内容”

## 两轮分别是什么

**第 1 轮**（`round1/`，只用第 4 版的核心＋内置的“错误”类）：38 / 39。写的过程中卡住或者别扭的地方：

1. 没法问“这段文字是不是数字”→ 第 17 条不过。
2. “空就用另一个”要写三句（取出来、如果是空、设成默认值）。
3. 一个“试着做”只有一个“出错了”的口，而且只能指定一个错误类 → “HTTP错误变响应”和“别的错误变 500”得写成两个中间件类（`错误处理`、`兜底`）套起来。
4. 没有“写到错误输出”→ 出错的细节只能打到标准输出，和正常日志混在一起。
5. 没有毫秒级的时间 → 记日志算不了耗时。
6. 仓库的“取出来 → 改 → 放回去”是三步，别的请求可能插进来（和 01 一样，按道理推的，没实测撞出来）。

**第 2 轮**（`libs/`、`app/`）：39 / 39。改了什么：

| 增补 | 属于哪层 | 改写了哪里 |
|---|---|---|
| 标准库函数 `isNumeric` | L2 | `校验` 的 `要数字` |
| 标准库函数 `orElse`（空就用另一个） | L2 | `仓库`、服务里的默认标签 |
| 宿主接口 `store.update` | L0 | `仓库` 的加、改、删 |
| 宿主接口 `log.error` | L0 | `错误处理` 默认把 500 的原因写到错误输出 |
| 宿主接口 `time.ms` | L0 | 记日志中间件算耗时（写到错误输出，不参加对比） |
| 不加新积木：一个“出错了”口里用“是不是某个类”分开处理 | — | `错误处理` 和 `兜底` 合成一个类 |
| 翻译规则：直接传给“不会等的地方”的匿名函数按“不许等”翻 | 翻译 | 让 `store.update` 在 Node 里能用 |

最后一行是第 2 轮自己撞出来的：`仓库` 改用 `store.update` 以后，**Python 全过，Node 这边却出错**（当时具体错了几条没有留下记录）——因为翻译脚本“调函数值一律等”，传给 `store.update` 的那个函数在 Node 里变成了“要等的”，宿主拿到的是“稍后的结果”而不是新值。这是这一轮最要紧的发现：**“一个函数要不要等”必须是函数类型的一部分**，不然两种语言会悄悄不一样（总文档 GAP-F1-09）。

第 2 轮还剩什么没解决，见总文档 `docs/blocks-v5-parts/F1-completeness-backend.md`。
